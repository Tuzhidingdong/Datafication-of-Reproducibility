# V1.0 Controlled Scientific Acceptance

## Purpose

V1.0 is the first controlled acceptance of the complete DOR workflow against real research material. It is **not** a bulk-corpus run and it is not permission to infer scientific meaning from filenames, column names, or model outputs.

The first pilot is deliberately limited to one primary paper/SI provenance relationship, selected by the executing Agent from the project's already-declared structured inputs when those inputs contain explicit source-location and SI-association metadata, plus only the structured records explicitly associated with that source. DoR does not read the paper or SI: they are retained only as provenance assets. The user remains the authority for scientific scope and approval; automatic candidate selection is a bounded operational selection, not scientific approval. This scope tests structured-data integrity, upstream extraction-record traceability, semantic mapping from structured fields and supplied metadata, canonical representation, and reconciliation. It does **not** establish cross-study predictive reproducibility or independently verify that upstream extraction matches the paper.

A single Study cannot support a Study-held-out train/test evaluation. Therefore, for a single-study pilot, `cohort_feasibility` and `modeling_validation` may be `NOT_APPLICABLE` only with an explicit reason. Do not manufacture Study groups, split rows as if they were independent Studies, or report model performance as scientific validation. Multi-study modelling acceptance is a later, separately scoped pilot.

## Non-negotiable limits

- Use only the bounded source set selected by the Agent under the deterministic source-selection procedure below. Do not scan or process the complete corpus.
- First inspect only the active project's declared source roots, registered Adapter Package, project configuration, and already-referenced CSV/JSON inputs. Do not scan the entire disk, unrelated projects, or an unregistered literature library.
- When declared CSV/JSON inputs contain original-source locations, the executing Agent must select one pilot candidate itself; it must not ask the user to choose among already identifiable candidates or repeat existing paths. Resolve source and SI relationships only from structured fields, registered metadata, and project configuration. For original paper/SI assets, check path existence, filesystem metadata, and byte-level SHA-256 only. Never open, parse, render, OCR, search, summarize, or test semantic readability of these files.
- Choose the candidate with the strongest metadata-backed traceability: prefer a paper whose primary-source and linked-SI identities/locations are explicitly represented in the structured inputs or project configuration and which has the greatest number of explicitly linked structured records. Break ties deterministically using the normalized source identifier, then normalized source path. A DOI-derived filename/path must be labelled as derived, not as a source-provided location. Do not open files to confirm their contents and do not use scientific-interest or outcome-based ranking.
- Include only records explicitly linked to the selected paper and its SI. Exclude unrelated papers and records with unresolved source identity, recording exact exclusion reasons. Do not treat a multi-paper aggregate as a single-paper dataset.
- If the structured inputs provide a paper location but no SI association/location, inspect only declared metadata and project configuration for an explicit SI relationship; do not search document contents or infer the relationship from a filename alone. If none is registered or resolvable, report that specific metadata gap. If no candidate source location can be resolved, report the exact missing field/path relationship and ask only for that missing information.
- Automatic selection does not authorize broad extraction, canonical construction, modelling, Worker dispatch, or bypassing G0-G4; the existing scope and approval gates remain unchanged.
- Original paper, SI, CSV, JSON, image, and other source files remain read-only. DoR may hash original-document bytes but must never read or interpret their contents; original documents are not analysis inputs.
- Hash every source at run initialization and compare it again before acceptance.
- Keep extracted/reported values separate from interpreted/normalized values; retain source locators and exact units.
- Preserve unresolved, missing, conflicting, and unverified information as such.
- Never infer experiment/replicate identity from row order or file layout.
- Never convert a statistical association or interaction into causality or mechanism.
- Do not dispatch a Worker silently. Before any Worker invocation, show role, provider, model, active project root, exact inputs, staging outputs, and constraints; wait for explicit authorization.
- Worker token counts are recorded only when actually returned. Missing usage remains unknown.
- A full PASS cannot retain blocking issue IDs. A schema-valid acceptance record is not proof of scientific correctness. Human review of the cited evidence is mandatory.

## Fixed acceptance stages

The stage list and order are fixed before execution. Do not merge or omit stages for convenience.

| Order | Stage | Required evidence / decision |
|---|---|---|
| 1 | `source_selection` | Agent-selected paper/SI candidate from declared inputs, reviewed scope statement; source inventory with exact paths and SHA-256; explicit exclusions. |
| 2 | `source_integrity` | Run initialization snapshot; source hashes verified unchanged; protected source roots and independent run workspace. |
| 3 | `extraction_review` | Review of the already supplied structured extraction records, their exact row/field locators, recorded upstream source locators, completeness, missingness, and declared uncertainty; human review of the structured handoff only. No paper/SI reading, OCR, or original-content spot-check. Upstream extraction fidelity remains explicitly outside DoR verification. |
| 4 | `semantic_mapping` | Explicit mapping from source fields/labels to canonical entities and condition/outcome definitions; exact units; grouping keys; unresolved semantics; G1 approval. |
| 5 | `canonical_reconciliation` | Canonical bundle validation; entity-grain diagnostics; reconciliation report/queue; source-to-canonical provenance; human decisions bound to exact hashes. |
| 6 | `cohort_feasibility` | Endpoint-specific coverage and exclusion report; explicit Study/Observation counts and split feasibility. If only one Study exists, record `NOT_APPLICABLE` for cross-Study modelling feasibility with the reason. |
| 7 | `modeling_validation` | Only for a predeclared multi-Study scope with sufficient independent Studies and G2 approval: Study-grouped baseline and nested evaluation, leakage checks, per-Study results, applicability limits. Otherwise `NOT_APPLICABLE` with a precise reason. |
| 8 | `publication_handoff` | Publication package manifest and integrity audit; every included claim/result linked to evidence and run artifacts; downstream Writing Skill guide; known limitations and exclusions. |

Each stage must be one of `NOT_STARTED`, `IN_PROGRESS`, `PASS`, `FAIL`, `BLOCKED`, or `NOT_APPLICABLE`. A `PASS` requires at least one exact evidence artifact (path + SHA-256). `NOT_APPLICABLE` requires a written scientific reason. `FAIL` and `BLOCKED` require a concrete blocker. A stage is not passed merely because its command exited with code 0. Stages cannot be marked IN_PROGRESS/PASS/FAIL/BLOCKED/NOT_APPLICABLE until all preceding stages are PASS or NOT_APPLICABLE; a FAIL/BLOCKED stage stops all later work in this acceptance record. In a single-Study scope, only cohort_feasibility and modeling_validation may be NOT_APPLICABLE.

## Boundary with the Run Plan

The Controlled Acceptance Record is intentionally a **post-Run project-level artifact**, not a stage output inside the Run Plan it evaluates. It verifies the completed Run Manifest, the complete Run Event Ledger, the G0-G4 Gate Ledger, source snapshots, and exact stage outputs. Its append-only revision ledger and detached checkpoint then preserve the independent review history.

Putting the Acceptance Record inside the same Run would create a circular trust dependency: the record must bind the final Run Event Ledger, while recording the Acceptance Record as a successful Run stage would itself append a later Run Event and change the ledger the record had just accepted. Therefore the operational Run DAG ends with its declared review/promotion and publication stages; after those stages are complete, create, validate, revise, and externally checkpoint the separate Acceptance Record. A new material source/plan requires a new Run and a new Acceptance Record; do not mutate the accepted Run to include the record.

## Run-bound provenance sources and post-Run initialization

The Run Plan may declare a separate top-level `acceptance_source_artifacts` array. This is deliberately distinct from `source_artifacts`:

- `source_artifacts` are operational inputs consumed by declared Run stages.
- `acceptance_source_artifacts` are provenance-only sources used by the post-Run V1.0 Acceptance Record. They are never Stage inputs and must never be passed to a Worker or opened by DoR.

Declare only the exact sources needed for the controlled Acceptance scope. Every path must be absolute, exist at Run initialization, and be inside one of the declared `source_roots`. The Runtime stores each `source_id`, `role`, exact path, and SHA-256 in the immutable Run Manifest and verifies the bytes again when the Run is checked. Use these roles:

- `PRIMARY_PAPER`
- `SUPPLEMENTARY_INFORMATION`
- `STRUCTURED_DATA`
- `OTHER`

Create the project Run Plan with the source list passed explicitly to the Runtime helper. The helper places these sources in the separate provenance-only snapshot and includes their parent directories in the protected source roots:

    dor init-run-plan --adapter-handoff <preflight_handoff.json> --project-root <project_root> --run-root <new_run_root> --acceptance-source SOURCE_PRIMARY_PAPER=PRIMARY_PAPER=<primary_paper_path> --acceptance-source SOURCE_SUPPLEMENTARY_INFORMATION=SUPPLEMENTARY_INFORMATION=<linked_si_path> --acceptance-source SOURCE_STRUCTURED_DATA=STRUCTURED_DATA=<structured_data_path>

Do not hand-edit `acceptance_source_artifacts` into the generated Run Plan. If another source is required, create a new Run Plan with the complete explicit source list and initialize a new Run. The command hashes and records these files only; it never reads paper/SI contents or makes them computational Stage inputs.

A one-Study controlled Acceptance must include at least one `PRIMARY_PAPER` and one `SUPPLEMENTARY_INFORMATION` entry. These roles establish provenance identity only; they do not authorize content inspection. A changed or missing provenance source blocks acceptance and requires a new immutable Run snapshot.

After the Run has completed every declared stage (all stages are current or explicitly SKIPPED), prepare two post-Run records using the templates and the exact source IDs/paths/hashes in `run_manifest.json`:

- `templates/v1_source_selection_manifest.example.json`: selected and excluded sources must partition the entire `acceptance_source_artifacts` snapshot exactly; every excluded item needs a reason. Its `study_ids` must equal the explicit sorted Study IDs in the Run Canonical Bundle.
- `templates/v1_extraction_review_record.example.json`: `source_hashes` must exactly bind the sources in `selected_sources` (not excluded sources). Excluded sources remain in the complete source-selection partition with their exact hashes and reasons, but are not extracted/reviewed. Review only the supplied structured CSV/JSON records and opaque locator metadata. Do not dereference paper/SI locators. Use `UPSTREAM_EXTRACTION_UNVERIFIED` for a structured record whose upstream extraction fidelity is outside DoR's scope, and `NOT_APPLICABLE` when no structured locator is expected for a provenance-only paper/SI source. `REVIEW_REQUIRED` prevents a PASS.

Initialize the post-Run draft and its append-only revision ledger in one operation:

```bash
dor init-acceptance --manifest <run_root>/run_manifest.json --out <acceptance_root>/acceptance_record.json --source-selection-manifest <acceptance_root>/source_selection_manifest.json --extraction-review-record <acceptance_root>/extraction_review_record.json --actor "<reviewer>" --rationale "Initialize acceptance for the completed Run"
```

The command refuses an incomplete/stale Run, verifies the two post-Run evidence files against the immutable source snapshot, derives Study IDs from the Canonical Bundle, and binds the final Run Event Ledger and current G0-G4 Gate Ledger. It creates all eight Acceptance stages as `NOT_STARTED`; it does not mark a scientific stage PASS, approve a Gate, or decide the final outcome. It also initializes the sibling `acceptance_record_acceptance_events.jsonl` revision ledger. Inspect the generated draft, complete each human review in the fixed order, register every edit with `dor record-acceptance-revision`, and validate with `dor validate-acceptance`. Do not use a hand-edited draft as accepted history without recording its revision.

The two post-Run evidence records are separately hashed Acceptance evidence, not Run outputs. They must remain unchanged after initialization; changes require an Acceptance revision and fresh validation. The original paper/SI bytes are only hash-checked, never read.

## Operational Run Plan support for the single-Study protocol

The formal Run Manager now has a dedicated `CONTROLLED_SINGLE_STUDY` execution profile for both Adapter routes. It reuses the normal route through G2, then binds the human applicability record, deterministic validation, and explicit NOT_APPLICABLE outputs before G3, Worker review, G4, and Publication Package audit. This does not omit G0-G4 or change the scientific acceptance stage order.

Select the matching profile template described in `docs/RUN_PLAN_EXECUTION_BINDINGS.md`. The two N/A Acceptance stages must each cite the same Run-bound applicability record and validation report, together with the exact Canonical Bundle and Modeling Task. The validator verifies their hashes and confirms that the one eligible Study is the only reason a three-way independent-Study split cannot be formed.

## Approval and execution sequence

1. Inspect the declared project inputs and select one paper/SI candidate using the deterministic, traceability-first procedure in Non-negotiable limits. Report the selected candidate, selection rationale, exact source paths/hashes, linked structured-record coverage, and exclusions to the user. Ask only when a required source relationship cannot be resolved from existing project data.
2. Prepare the full Run Plan DAG before running any stage. Each independent Runtime operation and artifact-reuse boundary is a separate stage. Declare operational source artifacts, the separate provenance-only `acceptance_source_artifacts` snapshot, dependencies, inputs, outputs, executor, and G0-G4 gates explicitly.
3. Initialize a new Run. Verify source hashes and the initialization event. Do not put run outputs under a protected source root.
4. Complete source audit and structured extraction-record review using only the declared CSV/JSON and supplied metadata. Present source inventory, structured-record coverage, recorded locators, missingness, uncertainties, and scope to the user. Do not open or inspect original-document contents. Stop for G0.
5. Prepare mapping and build specifications only from structured fields, supplied data dictionaries/domain configuration, and explicit user-provided metadata. Present entity-grain choices, exact units, mapping uncertainties, and validation reports. If a field meaning or value cannot be established from the structured handoff, leave it unresolved and request an upstream structured correction; do not inspect the original paper/SI. Stop for G1.
6. Build and validate the canonical bundle; reconcile without automatic merge, deletion, averaging, or source selection. Record human decisions separately.
7. Assess cohort feasibility. Do not run modelling until the exact task and cohort are approved at G2. A single Study is insufficient for Study-level held-out validation.
8. If a multi-Study analysis is approved, execute baseline and nested Study-grouped validation; then interaction discovery and robustness only when the declared data support them. Keep G3 selection explicit and G4 finalization separate.
9. Assemble and audit the publication package. Verify every artifact hash and evidence link before marking handoff complete.
10. After all Run stages are current, prepare the source-selection and structured extraction-review records, then create the post-Run Acceptance draft and revision ledger with `dor init-acceptance`. Complete the eight stage reviews in order, register revisions, validate the record, and retain a detached checkpoint. Record the final decision and limitations. Conditional acceptance means the tested scope passed while explicitly listed capabilities remain unvalidated; it must not be presented as full scientific validation.

## Acceptance decisions

- `NOT_ASSESSED`: stages are incomplete or the human acceptance review has not occurred.
- `PASS`: every fixed stage is `PASS`. This is not expected for a one-Study pilot because cross-Study modelling cannot be validated from one Study.
- `CONDITIONAL_PASS`: all applicable stages pass; every `NOT_APPLICABLE` stage has a defensible reason; no unresolved blocking issue remains for the declared scope. State exactly what has and has not been accepted.
- `FAIL`: a required stage failed or a critical provenance/scientific safeguard was violated.

Do not mark a blocked or failed stage as passed to obtain a green summary. A revised source snapshot or materially changed analysis plan requires a new Run and a new acceptance record; preserve the prior record.

## V1.0 boundary

V1.0 acceptance is complete only when an Agent-selected real-data pilot candidate has been reviewed by the user, its scope has been approved, and its evidence package is complete. Synthetic CI remains necessary engineering evidence but is not a substitute for this acceptance. No real corpus has been processed as part of this protocol's implementation.


## Acceptance revision history

The acceptance record is a reviewable state document, not an editable source of truth by itself. Every acceptance record must have a separate append-only JSONL revision ledger and immutable snapshots in the sibling `<ledger>.revisions/` directory. The first event is created once; later events bind the exact record SHA-256, actor label, timestamp, rationale, prior event hash, and the accepted stage/final-decision state. The event chain and snapshot bytes are checked by `validate-acceptance`.

For a new Run-bound V1.0 record, use `dor init-acceptance` as described in **Run-bound provenance sources and post-Run initialization**; it creates the Acceptance draft and sibling revision ledger together. Use `dor init-acceptance-ledger` only when initializing a separately prepared legacy/manual record that does not already have a revision ledger:

```bash
dor init-acceptance-ledger --record acceptance_record.json --ledger acceptance_events.jsonl --actor "reviewer" --rationale "Created the controlled acceptance record."
```

Never run ledger initialization a second time for a record that already has its sibling ledger.
After editing a stage review, register the revision rather than treating the edited JSON as accepted:

```bash
dor record-acceptance-revision --record acceptance_record.json --ledger acceptance_events.jsonl --actor "reviewer" --rationale "Re-reviewed source selection against the updated source inventory."
```

A stage revision must carry fresh `reviewed_by`, timezone-aware `reviewed_at`, and `review_rationale` metadata for any terminal review status (`PASS`, `FAIL`, `BLOCKED`, or `NOT_APPLICABLE`). The revision command identifies the earliest changed stage, preserves that stage's new review, automatically resets every later stage to `NOT_STARTED`, clears its evidence/checks/review metadata, and changes the final assessment to `NOT_ASSESSED`. The old final PASS therefore cannot survive an upstream stage revision. Re-review and revalidation must then proceed in fixed stage order. A final decision change without a stage change is recorded as its own event and requires `assessed_by`, timezone-aware `assessed_at`, and rationale.

Changes to `acceptance_id`, project/run identity, scope, Run Manifest hash, or source snapshot are not revisions of the same acceptance: create a new Run/Acceptance Record and preserve the previous history. Direct edits not followed by a revision event fail ledger validation because the current record no longer matches the latest immutable snapshot. Do not delete or rewrite prior snapshots/events. The SHA-256 chain is tamper-evident, but it is not a digital signature and does not independently authenticate the actor label.

If a process stops after committing the immutable event but before replacing the current JSON record, restore only the exact precommit state:

```bash
dor recover-acceptance-record --record acceptance_record.json --ledger acceptance_events.jsonl
```

Recovery refuses any unrelated/manual edit. Validation remains read-only.

Inspect the verified review timeline without modifying it:

```bash
dor acceptance-history --ledger acceptance_events.jsonl
```

The output includes each revision's actor label, recorded timestamp, rationale, changed stage, automatically invalidated downstream stages, final decision, event hash, and immutable snapshot path.

Validation now requires the ledger explicitly:

```bash
dor validate-acceptance --record acceptance_record.json --run-manifest <run-root>/run_manifest.json --ledger acceptance_events.jsonl --out acceptance_validation_report.json
```


## Detached Acceptance checkpoints and the external trust boundary

A hash-chained ledger detects accidental damage and edits that do not recompute the entire history. It cannot, by itself, prove that a fully privileged actor did not replace the current record, every snapshot, and the complete event chain together and then recalculate all hashes. A hash stored only beside those writable files is not an independent trust anchor.

Create a detached checkpoint after a reviewed revision:

~~~bash
dor checkpoint-acceptance \
  --record acceptance_record.json \
  --ledger acceptance_events.jsonl \
  --out acceptance_checkpoint.json
~~~

The command verifies the current record against the latest revision, inventories every immutable snapshot, and captures the Acceptance ledger tip plus any bound Workflow Gate and Run Event ledgers. It prints the checkpoint_sha256 value. The detached format is defined by `schemas/v1_acceptance_checkpoint.schema.json`; the verifier also enforces exact field sets, strict integer types, SHA-256 formats, and contiguous snapshot numbering before comparing live state.

Then retain both the checkpoint JSON and the printed SHA-256 in a separate trust domain (for example, an independently controlled records repository, signed release, institutional archive, or write-once store). Do not rely on keeping the checkpoint and its digest only in the same writable project directory.

Verify at any later time using the independently retained digest:

~~~bash
dor verify-acceptance-checkpoint \
  --record acceptance_record.json \
  --ledger acceptance_events.jsonl \
  --checkpoint acceptance_checkpoint.json \
  --expected-sha256 <independently-retained-checkpoint-sha256>
~~~

The verifier checks the checkpoint file against the trusted digest, then compares the current Acceptance Record, complete event ledger, every snapshot, and bound upstream ledgers with the anchored state. An exact match is reported as CURRENT_MATCH. Later legitimate Acceptance revisions are reported as APPEND_ONLY_EXTENDED only when the anchored event tip and every snapshot remain an exact prefix, and any previously bound Gate/Run ledger also preserves its prior event history. A shorter history, replaced prefix, or unrecorded upstream change fails. After a new review is accepted, create and independently retain a new checkpoint for the latest state. Coordinated local rewrites and rollback are detected provided the independent digest remains trustworthy. If the checkpoint and its expected digest are both replaced in the same compromised trust domain, the check cannot establish the original history.

This mechanism is tamper-evident anchoring, not a digital signature, trusted timestamp, reviewer identity provider, or proof of scientific correctness. Create a new checkpoint after an accepted revision and preserve prior checkpoints; never overwrite the old checkpoint.

## Deterministic record validation

After filling the acceptance record, run:

    dor validate-acceptance --record acceptance_record.json --run-manifest run_manifest.json --ledger acceptance_events.jsonl --out acceptance_validation_report.json

The validator checks the exact eight-stage order, duplicate/missing stages, stage status requirements, explicit unique Study IDs and their count, one-Study constraints, final decision consistency, and the current SHA-256 of every source and evidence file. It also checks every cited Run artifact against the regenerated Run artifact manifest: only artifacts whose producer stage and dependency chain are currently `REUSE` may support acceptance. A previously successful artifact marked `STALE_OR_MISSING`, `REBUILD_REQUIRED`, or `INVALIDATED_BY_UPSTREAM` cannot be reused merely because its old file and hash still exist. Every evidence entry must also declare an `artifact_type`; the implementation-owned V1.0 stage contract checks the required type set and reads each exact Run-bound JSON file to validate its content. A caller cannot replace the fixed checks by supplying a weaker list. It first verifies the Run Manager plan and hash-chained event ledger; the acceptance source list must exactly match the Run Manifest source IDs, paths, and initialization hashes. Evidence must resolve to a declared source artifact or an output recorded as successfully completed by this Run, with the exact path and event/source SHA-256. Relative file paths resolve from the acceptance-record directory. The validator is read-only and returns exit code 2 when any check fails. It does not parse scientific meaning, inspect whether a cited figure/table truly supports a claim, authenticate reviewer identity, or replace human approval.


## Deterministic content assertions

Every stage marked `PASS` must include at least one machine-evaluated content assertion in its `checks` array. A check references an artifact already attached to that same stage's evidence list and declares an RFC 6901 JSON Pointer plus an operator. The Runtime reads the exact Run-bound JSON artifact and computes the result; a caller cannot submit a claimed result field.

Supported operators are `exists`, `equals`, `not_equals`, `gte`, `lte`, `non_empty`, `unique`, and `contains`. Operators requiring a comparison value must include `expected`. Numeric comparisons reject booleans and non-numeric values. `unique` compares canonical JSON values. Missing pointers, invalid JSON, unsupported operators, evidence not attached to the same stage, and failed assertions are validation errors.

Example:

```json
{
  "check_id": "canonical_bundle_has_explicit_studies",
  "artifact_id": "canonical_bundle",
  "json_pointer": "/studies",
  "operator": "non_empty"
}
```

These assertions remain supplemental checks. The stage-specific evidence contracts are fixed in `docs/V1.0_STAGE_EVIDENCE_CONTRACTS.md` and are evaluated automatically for every PASS stage. The contracts enforce file types, required fields, entity links, exact source and artifact hashes, Study ID coverage, and model split consistency. Generic JSON Pointer checks cannot weaken or replace those fixed validations. The contracts do not establish that the extraction is scientifically faithful, a semantic mapping is appropriate for the approved domain, or model performance is useful; those decisions still require domain review.


## Stage contract and evidence descriptor

Every evidence descriptor must include `artifact_type` in addition to `artifact_id`, `path`, and `sha256`. For a stage to PASS, the validator requires the exact artifact types in the implementation-owned registry. For example, `canonical_reconciliation` requires `canonical_bundle`, `reconciliation_report`, and `reconciliation_decisions`; their payloads are read from the verified files, and the report's `bundle_sha256` must equal the bundle evidence hash. The Cohort report exposes `eligible_study_ids`; the split must cover those exact eligible Studies, and the model run's Study assignments must match the accepted split. Missing types, unsupported types, malformed content, or cross-artifact mismatches block PASS.


For `modeling_validation`, a PASS must cite the serialized `model_artifact` in addition to the model report/run manifest, and the nested Study-grouped evaluation report plus its manifest. The evaluation contract requires at least four eligible Studies and checks that each is held out exactly once with no outer or inner Study leakage.

Canonical reconciliation PASS also requires a Run-bound `reconciliation_decisions` artifact. The validator checks those human decisions against the exact report and canonical bundle hashes; all CRITICAL and REVIEW_REQUIRED issues need explicit decisions and may not remain unresolved. Cohort feasibility PASS requires the exact `modeling_task`, `cohort_report`, `split_manifest`, `modeling_cohort_manifest`, and hash-verified `modeling_cohort.csv`. Their task identity, eligible Study set, and input/output hashes must match. The CSV is a hash-only artifact and is never parsed as JSON.


The final `publication_handoff` stage is independently audited during acceptance. Its manifest evidence must resolve to the package's root `package_manifest.json`; the separate integrity report is checked against a fresh run of the package auditor over that exact directory. The validator does not accept a self-reported `valid=true` as proof. It checks guide and artifact SHA-256 values, indexed versus actual package files, completeness derivation, and package path safety.


The source-selection record partitions every input captured in the Run snapshot into selected or excluded. Exclusions require a source ID, role, exact path/hash, and reason; source inventory entries must originate only from selected inputs. The Run snapshot defines available inputs, not an obligation to analyze every file.

### Cross-ledger G0-G4 binding

A final `PASS` must include `workflow_gate_ledger` in the Acceptance Record. It binds the workflow-gate JSONL path, exact ledger SHA-256, latest event hash for each G0-G4, and the complete artifact-reference list (artifact ID, absolute path, SHA-256) from each latest gate event. Whenever a Gate ledger is bound, the validator checks its live hash-chain integrity, ledger digest, latest event hashes, and recorded artifact lists. The additional cross-ledger acceptance requirement is enforced for a final `PASS`: every gate must overlap at least one PASS-stage Acceptance Evidence artifact by the same ID, resolved path, and SHA-256. An ID match with a different path or hash is rejected. While the final decision is `NOT_ASSESSED`, `FAIL`, or otherwise not a full `PASS`, this overlap requirement is deferred; stage revisions can therefore invalidate downstream Acceptance Evidence without making the still-pending record structurally invalid. A later final `PASS` is still blocked until every gate has current accepted evidence. In particular, G3 must explicitly include at least one accepted cohort artifact in its approval packet (for example, cohort report, split manifest, or modeling cohort manifest), alongside its interaction-selection materials. A final `PASS` also binds the Run Event Ledger path, SHA-256, event count, and latest event hash. Both Gate and Run ledgers are checked against their live hash-chained files. Any appended decision, changed artifact, stale upstream dependency, revoked approval, or changed Run event invalidates the corresponding binding. Rebinding either upstream ledger is an explicit `UPSTREAM_LEDGER_RECORDED` revision: the new ledger must extend the previously bound hash chain at the same path, all eight Acceptance stage reviews and the final decision are invalidated, and rollback to an earlier event tip is rejected. Initial upstream ledger bindings may be captured with the explicit final-decision review. These cross-ledger checks record provenance; they do not authenticate reviewer identity or establish scientific correctness.
