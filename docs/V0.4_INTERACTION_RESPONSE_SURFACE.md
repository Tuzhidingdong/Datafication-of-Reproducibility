# V0.4 — Pairwise interaction response surfaces

## Purpose and use

The response-surface stage turns one explicitly selected pair from a completed, hash-verified interaction catalogue into plotting data. It is intended for interpreting the fitted model over the observed range of two numeric conditions. It does not perform new interaction discovery and does not establish causality.

The initial implementation supports numeric × numeric pairs only. Categorical and mixed pairs are rejected with an explicit error rather than forced onto continuous axes.

## Fit protocol

The surface model is a descriptive refit using all eligible cohort observations and the median interaction Ridge alpha selected in the nested folds for that pair. It reuses the exact pairwise bilinear design basis from the discovery engine: the full task-defined additive feature matrix plus the selected pair's encoded product.

This all-cohort refit is deliberately labelled `ALL_COHORT_DESCRIPTIVE_REFIT_FROM_MEDIAN_NESTED_ALPHA`. It is not an independent validation result and must not be used to report cross-study prediction performance. The source interaction catalogue and manifest are hash-checked against the exact cohort and task before fitting.

## Partial-dependence surface

For each point on a regular grid across the selected pair's task-configured quantile range, the two focal features are set to that grid coordinate. Other task features retain their observed values in a deterministic background sample, and predictions are averaged across those rows.

This is partial dependence, not a conditional response estimate. Correlated covariates may yield combinations that are unrealistic even when the two focal values are common. The report records the background sample size and selection method. The runtime enforces a hard cap of 500,000 partial-dependence row evaluations per surface; reduce grid size or background size if the requested product exceeds this budget.

## Empirical 2D support mask

Each grid point receives one of four support labels:

- `SUPPORTED_EMPIRICAL_2D_REGION`: inside the convex hull of observed pair values and no farther than the configured quantile of leave-one-out nearest-neighbour distances.
- `LOW_LOCAL_DENSITY`: inside the convex hull but beyond the empirical nearest-neighbour distance threshold.
- `OUTSIDE_OBSERVED_CONVEX_HULL`: outside the convex hull of observed pair values.
- `SUPPORT_NOT_ESTIMABLE`: the observed pair values do not define a non-degenerate two-dimensional hull.

Distance is calculated after scaling each axis by its observed standard deviation. The default threshold is the 95th percentile of leave-one-out nearest-neighbour distances. These are descriptive geometric heuristics, not physical limits, calibrated probabilities, or proof of support in the complete multivariable condition space.

Only the selected two-feature projection is assessed. A point marked supported in this projection can still combine implausible values of other covariates.

## Marginal effects

The grid contains finite-difference partial derivatives of the predicted partial-dependence surface:

- `marginal_effect_feature_a`: change in predicted outcome per raw unit of feature A.
- `marginal_effect_feature_b`: change in predicted outcome per raw unit of feature B.
- `cross_partial_derivative`: the model's bilinear cross-partial derivative in outcome units per feature-A unit per feature-B unit.
- The report supplies explicit dimensional strings for both marginal effects and the cross-partial derivative, derived from the exact outcome and feature units in the task.

The cross-partial derivative is constant for this Ridge bilinear basis. It describes the fitted model algebra, not a physical interaction coefficient or causal effect. The two marginal-effect fields vary over the opposite feature axis when the bilinear term is non-zero.

## Command

Select the interaction ID from `interaction_catalogue.csv` after the required analysis review:

~~~bash
dor generate-interaction-surface \
  --cohort-dir 04_modeling/cohort \
  --task modeling_task.json \
  --interaction-dir 04_modeling/interactions \
  --interaction-id INT_<catalogue_id> \
  --out-dir 04_modeling/interaction_surfaces
~~~

Optional arguments:

- `--robustness-dir`: link the selected pair's repeated-seed robustness status after verifying its manifest.
- `--grid-size`: override task grid size (5–61).
- `--background-max`: override the deterministic partial-dependence background size (10–5000).

Task configuration:

~~~json
{
  "interaction_surface": {
    "grid_size": 21,
    "background_max_observations": 500,
    "range_quantiles": [0.0, 1.0],
    "support_distance_quantile": 0.95
  }
}
~~~

## Outputs

- `interaction_response_surface_report.json`: target/pair identity, descriptive model/refit details, surface method, support definition and counts, marginal-effect units, and claim limitations.
- `interaction_response_surface.csv`: gridded predicted response, support label/distance, both marginal effects, and cross-partial derivative.
- `interaction_observed_support.csv`: actual observed feature pairs, Study/Observation IDs, and observed target values for point overlays.
- `interaction_marginal_effects.csv`: compact source data for marginal-effect plots.
- `interaction_response_surface_manifest.json`: exact source and output hashes.

## Interpretation safeguards

- Plot unsupported regions as masked, hatched, or otherwise visually distinct. Do not make the whole grid appear equally data-supported.
- Overlay actual observations or density markers; never show the smooth surface without the empirical support data.
- A projected 2D support region is not a full-dimensional applicability domain.
- Partial dependence may combine correlated covariates unrealistically; inspect raw joint coverage and Study distribution before interpreting.
- A surface or slope is model-derived descriptive output, not evidence of causal modification, physical synergy, or a mechanism.
- Mechanism claims still require independent experimental, theoretical, or computational evidence and contradictory evidence must be recorded.

## Engineering tests

Synthetic tests cover a known bilinear response, derivative units, support labels, optional robustness linkage, exact manifest checks, numeric-pair restriction, input immutability, and output-directory protection. They are software checks only. Full real-corpus acceptance remains reserved for V1.0.
