# Run Plan execution bindings

## Mandatory structured-data-only boundary

Every DoR Run stage consumes only declared structured CSV/JSON datasets, supplied data dictionaries/project configuration, structured evidence-index records, and validated Canonical Bundles. Original papers, SI, images, and other raw research documents are provenance-only assets: DoR may register their identity/path and check filesystem metadata or byte-level SHA-256, but must never open, parse, render, OCR, index, search, summarize, or pass their contents to an LLM/Worker. Source locators in structured records are opaque references and must not be dereferenced. If required information is absent or ambiguous, record a blocker and request an upstream structured-data correction; do not reopen the original document. The `source_audit` action below reads only declared supported CSV/JSON artifacts.

This document is the human-facing operator guide for the two generic adapter Run Plans. The machine-readable source of truth for stage-to-action wiring is `runtime/src/dor/stage_execution_contract.json`; it binds each supported stage to its executor/action and exact route-specific inputs, outputs, gates, and activation condition. `dor run-init` validates this contract before creating a Run, and maintainers can preflight a template with `dor validate-execution-contract --plan <run_plan.json>`. Update the registry and its tests whenever a supported Run Plan or action changes. This contract defines execution wiring only; it does not define discipline-specific mappings, vocabularies, targets, or analysis assumptions.

All paths below are relative to the active Run workspace unless explicitly labelled as protected package or configuration paths. Resolve them from the current project configuration. Never substitute a hard-coded project path.

## Route preflight and Run initialization

Before choosing the formal Run Plan, determine the adapter route without auditing or modifying any source data:

    dor prepare-adapter-handoff --manifest <package_root>/adapter_manifest.json --package-root <package_root> --out <project_root>/run_control/adapter_route_preflight.json

Keep this preflight file outside the protected adapter package and outside all declared source/artifact files. A preflight result is only a package-integrity and route-selection result. For a STRUCTURED_DATASET route, do not run source audit before formal Run initialization. For a CANONICAL_BUNDLE route, the optional pre-Run Discovery scan is permitted but remains exploratory and does not approve G0-G2.

Select the matching Run Plan template, set its source roots, source artifact paths, workflow ledger path, and project/configuration paths from the active project configuration, then initialize a new isolated Run:

    dor run-init --plan <selected_run_plan.json> --run-root <new_run_root>

Run Manager validates the declared source roots/artifacts and dependency graph, creates the Run workspace and `run_manifest.json`, and snapshots the exact plan/source inputs. Do not reuse an old Run root for a new plan. Verify initialization before stage execution:

    dor run-verify --manifest <run_root>/run_manifest.json

The first formal stage regenerates the handoff into the Run workspace. Do not use the preflight handoff as a Run output or copy it into the protected adapter package.

## Provenance-only sources for post-Run Acceptance

When the project will use V1.0 controlled Acceptance, add an explicit top-level `acceptance_source_artifacts` array to the selected Run Plan before `dor run-init`. Keep it separate from the operational `source_artifacts` list: these provenance-only files are not inputs to local Stage commands and must never be passed to a Worker. Each entry requires a unique `source_id`, one role (`PRIMARY_PAPER`, `SUPPLEMENTARY_INFORMATION`, `STRUCTURED_DATA`, or `OTHER`), and an absolute path inside a declared `source_roots` directory. For a `CONTROLLED_SINGLE_STUDY` Acceptance, declare both a primary paper and its linked SI. The Run Manager snapshots paths and SHA-256 only; it never opens their contents.

Example:

```json
{
  "acceptance_source_artifacts": [
    {"source_id": "SOURCE_PRIMARY_PAPER", "role": "PRIMARY_PAPER", "path": "/project/sources/paper.pdf"},
    {"source_id": "SOURCE_SUPPLEMENTARY_INFORMATION", "role": "SUPPLEMENTARY_INFORMATION", "path": "/project/sources/paper_si.pdf"},
    {"source_id": "SOURCE_STRUCTURED_DATA", "role": "STRUCTURED_DATA", "path": "/project/sources/paired_records.csv"}
  ]
}
```

At Run initialization, the list is hash-bound into `run_manifest.json` and the first Run Event. `dor run-verify` and `dor run-artifacts` report its independent integrity state. Changing or removing any declared source means the old Run no longer represents the same source snapshot; do not accept it.

After the Run has reached a terminal state (every stage current or explicitly SKIPPED), prepare:
- `templates/v1_source_selection_manifest.example.json` — partition every Acceptance source ID into selected or excluded exactly once, with reasons for exclusions and the sorted Study IDs from the exact Run Canonical Bundle.
- `templates/v1_extraction_review_record.example.json` — bind exactly the hashes for `selected_sources`; excluded sources remain in the source-selection partition with reasons and are not reviewed. Review only structured data rows/fields plus opaque upstream locator metadata. Never dereference an original paper/SI locator.

Create the project-level Acceptance draft and its revision ledger:

    dor init-acceptance --manifest <run_root>/run_manifest.json --out <acceptance_root>/acceptance_record.json --source-selection-manifest <acceptance_root>/source_selection_manifest.json --extraction-review-record <acceptance_root>/extraction_review_record.json --actor "<reviewer>" --rationale "Initialize acceptance for the completed Run"

The initializer fails closed if any Run stage is unresolved, a required Run artifact is stale, the single-Study profile lacks primary-paper/SI roles, the source-selection partition differs from the Run snapshot, the source inventory contains an excluded source, or the extraction-review hashes/locators are invalid. It derives `study_ids` from the Canonical Bundle, creates all eight Acceptance stages as `NOT_STARTED`, and records the current Run Event Ledger and G0-G4 Gate Ledger bindings. It does not approve or pass any Acceptance stage. The sibling `acceptance_record_acceptance_events.jsonl` and immutable revision directory are initialized in the same CLI operation.

Complete the human Acceptance stages in fixed order, recording each edit through `dor record-acceptance-revision`; then run:

    dor validate-acceptance --record <acceptance_root>/acceptance_record.json --run-manifest <run_root>/run_manifest.json --ledger <acceptance_root>/acceptance_record_acceptance_events.jsonl --out <acceptance_root>/acceptance_validation_report.json

Only an explicitly reviewed PASS/CONDITIONAL_PASS record can be checkpointed. Acceptance remains a separate post-Run artifact; never add it to the immutable Run DAG because that would change the Run Event Ledger tip it records.

## Contract-bound stage execution

Use Run Manager's action list as the execution queue. The Runtime now executes a declared local CLI stage and records its lifecycle in one operation; operators no longer need to issue separate `run-stage-record RUNNING` and `run-stage-record SUCCEEDED` commands for local work.

1. Inspect the queue and resolved paths:

       dor run-resume-plan --manifest <run_root>/run_manifest.json

2. Preview the next local stage. The Runtime resolves its complete argv from the machine-readable `argv_template` in `runtime/src/dor/stage_execution_contract.json`; the template references Run Artifact IDs rather than hard-coded project paths:

       dor run-stage-execute --manifest <run_root>/run_manifest.json --stage adapter_package_validation --dry-run

3. Advance all immediately executable local stages until a human, Worker, Gate, explicit user-choice, or failure boundary:

       dor run-advance --manifest <run_root>/run_manifest.json --max-local-stages 10

No per-stage argument JSON is required for either supported adapter route or the controlled single-Study profiles. The Runtime resolves Artifact paths and output directories from the active Run Plan, derives the package root from the validated adapter handoff, and injects the Run's workflow ledger/manifest for commands that require them. It never invokes a shell.

The runner obtains the allowed CLI subcommand from the checked-in execution contract. It invokes that subcommand with an argv array (never a shell), records RUNNING before launch, and records SUCCEEDED only after all declared output artifacts exist and can be hashed. It automatically supplies the Run's configured workflow ledger and exact manifest to commands that require them; callers must not override those trust-bound arguments. The command's working directory is the active Run workspace, so relative output paths resolve within that Run.

On a non-zero exit, timeout, launch error, or missing declared output, the runner records FAILED. Any partial files at declared output paths are preserved under `.dor_attempt_archive/<stage_id>/`; they are not silently deleted or left to block the next attempt. Before a retry or rebuild, pre-existing declared outputs are also archived with a manifest. Inspect archived results when diagnosing a failed stage; they are not current Run artifacts.

The runner deliberately refuses to execute MANUAL and WORKER stages. A MANUAL stage remains a human task: prepare the declared records, run the listed validator where applicable, then record the human stage as RUNNING/SUCCEEDED. A WORKER stage still requires `dor run-worker-authorize` and an explicit host Worker Manager dispatch; after the Worker writes only to its permitted staging path, record its terminal state and usage. Worker completion never substitutes for human review or G0-G4 approval. The queue should be re-read after every stage because upstream outputs, Gate decisions, and invalidations can change the next action.

This advances ready local stages in dependency order, automatically records inactive conditional stages as SKIPPED, and stops at the first human task, Worker authorization boundary, unapproved Gate, unresolved user-choice value, or execution failure. For a custom/unbound Run Plan only, an explicit `--args-dir` may supply per-stage argv overrides. For the supported plans, missing or ambiguous JSON values (such as a response-surface stage with more than one selected interaction ID) produce an `INPUT_REQUIRED` pause; the Runtime does not choose an item arbitrarily. After a human or Worker action is completed and recorded, invoke `run-advance` again. The default limit is ten local stages per call to keep each execution segment bounded.

## Host Worker Manager dispatch contract

Worker execution is deliberately delegated to the host Skill environment. Run Manager issues a bounded, hash-bound authorization packet; it does not spawn a process or choose a provider/model. The Skill must use the host's configured Worker Manager and follow this sequence:

1. Inspect the host Worker Manager and its currently available providers/models. Do not assume a provider, model, or session is available from a prior conversation.
2. Before starting, show the user the exact stage ID, role, provider, model, active project root, declared input artifact IDs, permitted output paths, task objective, forbidden actions, and token/output limits. Do not silently start a Worker or silently substitute another model. Obtain explicit authorization for that exact role/model/project.
3. Record authorization with `dor run-worker-authorize --manifest <run_root>/run_manifest.json --stage <stage_id> --role <role> --provider <provider> --model <model> --project-root <project_root> --authorized-by <reviewer> --rationale "<approved task and model>"`. The returned `task_packet` conforms to `schemas/run_worker_task_packet.schema.json`; it carries its exact `task_id`, `attempt`, and `authorization_event_hash`. The response also reports `task_packet_sha256`; preserve the packet and these identifiers in host job metadata when supported. The Run Event Ledger binds the deterministic task ID to this Run/Stage/Attempt, and a later Worker Result must return that same task ID.
4. Before dispatch, record RUNNING with the exact provider/model/project identity:
   `dor run-stage-record --manifest <run_root>/run_manifest.json --stage <stage_id> --status RUNNING --producer-kind worker --role <role> --provider <provider> --model <model> --project-root <project_root>`.
   This makes the in-flight attempt visible before an external process can start.
5. Dispatch only the returned task packet through the host Worker Manager. Tag the host job with the Run ID, Stage ID, and authorization event hash where the host supports job metadata. Capture the real job/session/task identifiers when returned. Monitor the host job until it reaches a terminal state; a submitted request is not completion.
6. Retrieve only the declared output; place it at the exact `worker_staging` path in the Run workspace. For the formal `worker_review_output`, `run-stage-record --status SUCCEEDED` now validates the complete Worker Result packet before appending success: top-level schema, result status, unique finding IDs, references restricted to declared Worker inputs, and exact evidence locators for every supporting artifact. A valid `partial` result is retained for human review; `blocked`/`failed`, malformed JSON, missing output, or invalid evidence is automatically recorded as FAILED instead, and the CLI returns non-zero. The Worker Result `task_id` must match the deterministic task ID in the exact DoR authorization packet. The separate host Worker Manager task ID is recorded as producer metadata only when the host actually returns one; the two identifiers must not be conflated. On any Worker FAILED event, every present staging output is moved to `.dor_attempt_archive/<stage_id>/attempt-<n>/`; the Run event binds the archive manifest and each archived file SHA-256. The declared staging path is clear for the next authorized attempt. `dor run-artifacts` lists the failed attempt under `archived_attempts` separately from reusable outputs. Record only the actual host job/session/task identifiers and usage fields returned by the Worker Manager; unknown usage stays null.
7. If the host job is still active after a reconnect, continue monitoring that same job using its identifiers or the Run/Stage/authorization tags. If its state is unknown or abandoned, inspect it before using `--confirm-abandoned`; a replacement attempt requires a fresh authorization packet. Never duplicate a potentially active job.

If the configured Worker Manager is unavailable before the stage is marked RUNNING, leave the stage blocked and report the missing host capability. If dispatch fails after RUNNING was recorded, append FAILED with a non-empty reason; Runtime archives any partial output and makes a fresh authorization/retry possible. For a structurally rejected result, Runtime performs the FAILED transition and archive automatically when SUCCEEDED was requested. Do not perform an invisible local substitute. The provider/model execution adapter belongs to the host environment; no provider-specific model catalogue or research-domain logic is embedded in DoR core.

## Stage status and artifact recording

Run Manager execution records are separate from the G0-G4 approval ledger. They do not create scientific approvals.

For the two supported adapter routes, `dor run-resume-plan` now returns a `next_actions` array. Each entry identifies the stage, current dispatch state, executor, required Gate, resolved input/output paths, and the corresponding Runtime command, validator command, or Worker authorization/host action. Use this output to select work; the operator commands and required arguments remain specified in the relevant stage table above. It is a plan only and never starts a command, Worker, or approval.

- Before a command starts, record the stage as RUNNING with `dor run-stage-record --manifest <run_root>/run_manifest.json --stage <stage_id> --status RUNNING --producer-kind <local|worker|manual> --command "<exact CLI command>"`.
- After checking all declared outputs and their hashes, record SUCCEEDED with the same stage ID and producer metadata. Record FAILED when the command or its output validation fails; never record success for a partial output set.
- For a conditional stage, consult `dor run-resume-plan`. Record `SKIPPED` only when its action is exactly `SKIP_REQUIRED`, using the stage's declared executor as `--producer-kind`. A skipped stage writes no outputs, creates no approval, and is reusable only while its declared activation input remains unchanged and the condition remains false.
- For a Worker stage, include the exact role/provider/model and returned job/session/task identifiers plus available usage fields in the RUNNING/SUCCEEDED records. For a manual stage, use `--producer-kind manual` and record the reviewer context in the rationale/command metadata.
- Run `dor run-verify --manifest <run_root>/run_manifest.json` after a stage boundary that changes artifact lineage. Use `dor run-resume-plan --manifest <run_root>/run_manifest.json` after interruption; do not rerun successful unaffected stages.
- Conditional activation is declared on a stage as `activation: {artifact_id, json_pointer, operator, value?}`. The activation artifact must also be an explicit stage input. Supported operators are `exists`, `not_exists`, `array_non_empty`, `array_empty`, `boolean_true`, `boolean_false`, `equals`, and `not_equals`. JSON Pointer evaluation occurs only after the activation artifact's producer is currently reusable. The scheduler does not infer or rewrite activation data.

The Canonical Bundle path is route-dependent: resolve the `canonical_bundle` artifact by ID from `dor run-artifacts` rather than hard-coding one template's directory. In the structured route it is produced by `canonical_build`; in the canonical-adapter route it is the verified materialized bundle. The modeling-task, cohort, interaction, robustness, response-surface, and mechanism-plan paths above are the Run-relative paths declared by both templates. Resolve them from the active `run_root`, not from a prior Run or project-global working directory.

## Execution and approval rules

1. The Skill resolves paths from the active project and Run configuration; it does not copy paths from this document literally.
2. Before an active stage runs, confirm that all declared inputs exist, hash-match the Run artifact manifest, all direct dependencies are reusable, and its required gate is currently approved. 3. Execute only the command bound to that stage. Do not substitute a different command because two outputs have similar names.
4. After command success, verify every declared output exists and record its exact hash and stage status with Run Manager.
5. Manual stages remain manual. A completed command, valid package, valid bundle, or generated review packet is not an approval.
6. Gated commands receive the active workflow ledger. Do not use a legacy bypass.
7. When an upstream input hash changes, follow Run Manager's resume plan and repeat only the invalidated downstream stages.
8. The two Run Plan templates declare the post-selection stages explicitly. If `selected_interaction_ids` is empty, the mechanism-plan preparation, response-surface, and mechanism-evidence-bridge stages are recorded as `SKIPPED`; no G3 mechanism-plan binding or optional analysis output is fabricated.
