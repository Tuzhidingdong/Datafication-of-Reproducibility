# V0.2 — Data Understanding Engine

## Purpose

V0.2 prepares evidence for a human-approved canonical mapping without silently deciding what a row, JSON object, field, or reported value means scientifically.

## Implemented foundation

- CSV row-shape checks distinguish short rows, long rows, and consistent rows.
- Nested JSON profiling records bounded structural paths, JSON value types, and list-length ranges.
- JSON profile output omits raw source text values.
- Both profiles are explicitly structural; neither is a domain mapping.
- The project schema accepts the documented top-level notes field in the example configuration.

## Canonical entity model

The framework distinguishes Study, System, Condition, Experiment, Observation, Comparison, and Evidence. The mapping layer must support one-to-many and many-to-many relationships where justified. It must not assume one CSV row equals one experiment or replicate, nor that one nested JSON object has a universal meaning across domains.

## Mapping contract

Every mapped field should retain a stable canonical field ID; source file hash and source row/object locator; source column or JSON path; raw value and raw unit; normalized value and normalized unit if approved; conversion record; missingness state; evidence locator; mapping rule ID and version; review status and reviewer decision.

Mapping status values are PROPOSED, REVIEWED, APPROVED, REJECTED, or UNRESOLVED. Only approved mappings may feed a scientific modelling cohort. Raw source content remains immutable.

## Missingness and conflicts

Use REPORTED, NOT_REPORTED, NOT_APPLICABLE, AMBIGUOUS, CONFLICTING, and NOT_ASSESSED. Do not convert an absent JSON key or blank CSV cell into zero or a common default. Conflicting source passages remain separately traceable until reconciled.

## Planned output artifacts

The intended V0.2 outputs are data_audit_report.md, dataset_manifest.json, column_coverage.csv, json_structure_paths.csv, source_inventory.json, mapping_candidates.json, mapping_review_queue.csv, and entity_relationship_report.md. Only the first four are generated by the current runtime. The remaining artifacts require source-specific parsing and human review and are not represented as implemented.

## Acceptance boundary

Engineering fixtures may test nested shapes, missing keys, malformed rows, duplicate identifiers, and conflicting records. They must not be presented as scientific validation on the user's real corpus. Complete end-to-end scientific acceptance is reserved for V1.0.
