# V0.2 — Data Understanding Engine

## Purpose

V0.2 prepares evidence for a human-approved canonical mapping without silently deciding what a row, JSON object, field, or reported value means scientifically.

## Implemented foundation

- CSV row-shape checks distinguish short rows, long rows, and consistent rows.
- Nested JSON profiling records bounded structural paths, JSON value types, and list-length ranges.
- JSON profile output omits raw source text values.
- A deterministic source inventory assigns stable IDs from source hash plus locator.
- A mapping review queue exposes every CSV column and observed JSON path as UNRESOLVED; it does not guess canonical field meanings.
- A canonical research bundle schema defines Study, System, Condition, Experiment, Observation, Comparison, and Evidence entities.
- A runtime validator checks canonical required fields, duplicate IDs, cross-entity references, selected relationship constraints, missingness vocabulary, and evidence locators.
- A mapping-plan schema and validator check source-inventory identity, source references, mapping status, canonical targets, explicit transformations, approval metadata, and duplicate approved targets.
- Both source profiles are explicitly structural; neither is a domain mapping.

## Canonical entity model

See [Canonical research data model](CANONICAL_DATA_MODEL.md) for definitions, relationship rules, endpoint separation, missingness, provenance, and validation boundaries.

The mapping layer must support one-to-many and many-to-many relationships where justified. It must not assume one CSV row equals one experiment or replicate, nor that one nested JSON object has a universal meaning across domains.

## Mapping contract

See [Mapping contract](MAPPING_CONTRACT.md) for the complete mapping-plan structure and approval rules.

Mapping status values are PROPOSED, REVIEWED, APPROVED, REJECTED, or UNRESOLVED. Only APPROVED rules that pass deterministic validation are eligible for canonical construction. Raw source content remains immutable. Transformations are declared, versioned instructions; the validator does not execute them.

## Missingness and conflicts

Use REPORTED, NOT_REPORTED, NOT_APPLICABLE, AMBIGUOUS, CONFLICTING, and NOT_ASSESSED. Do not convert an absent JSON key or blank CSV cell into zero or a common default. Conflicting source passages remain separately traceable until reconciled.

## Current output artifacts

The runtime currently generates data_audit_report.md, dataset_manifest.json, column_coverage.csv, json_structure_paths.csv, source_inventory.json, and mapping_review_queue.csv. It can validate a mapping plan against that exact source inventory and validate a canonical bundle. Source-specific conversion into canonical entities is not yet automated.

## Planned next artifacts

The next component is a canonical data builder that consumes only an approved mapping plan and preserves raw values, transformation records, and source provenance. Relationship-level diagnostics (including possible duplicates, orphaned entities, and endpoint conflicts) will be developed separately and will not silently merge records.

## Acceptance boundary

Engineering fixtures may test nested shapes, missing keys, malformed rows, duplicate identifiers, conflicting records, mapping approval gates, and stale provenance. They must not be presented as scientific validation on the user's real corpus. Complete end-to-end scientific acceptance is reserved for V1.0.
