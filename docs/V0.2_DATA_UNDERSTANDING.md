# V0.2 — Data Understanding Engine

## Purpose

V0.2 prepares evidence for a human-approved canonical representation without silently deciding what a row, JSON object, field, or reported value means scientifically.

## Implemented foundation

- CSV row-shape checks distinguish short rows, long rows, and consistent rows.
- Nested JSON profiling records bounded structural paths, JSON value types, and list-length ranges.
- JSON profile output omits raw source text values.
- A deterministic source inventory assigns stable IDs from source hash plus locator.
- A mapping review queue exposes every CSV column and observed JSON path as UNRESOLVED; it does not guess canonical field meanings.
- A canonical research bundle schema defines Study, System, Condition, Experiment, Observation, Comparison, and Evidence entities.
- A runtime validator checks canonical required fields, duplicate IDs, cross-entity references, selected relationship constraints, missingness vocabulary, and evidence locators.
- A mapping-plan schema and validator check source-inventory identity, source references, mapping status, canonical targets, explicit transformations, approval metadata, and duplicate approved targets.
- A canonical build specification declares entity grain, grouping keys, mapped fields, and child-parent links.
- A deterministic CSV builder consumes only validated APPROVED mapping rules, preserves raw-cell provenance, creates stable IDs, and validates the resulting canonical bundle before writing it.
- Source JSON is structurally inventoried but not yet supported as an executable canonical build selector.

## Canonical entity model

See [Canonical research data model](CANONICAL_DATA_MODEL.md) for definitions, relationship rules, endpoint separation, missingness, provenance, and validation boundaries.

The model does not assume one input row equals one experiment or replicate. Entity granularity is explicitly declared through SOURCE_ROW or GROUP_BY_FIELDS rules. Grouped field conflicts cause a build failure; the builder does not select an arbitrary row or average values.

## Mapping and construction contracts

See [Mapping contract](MAPPING_CONTRACT.md) and [Canonical Builder contract](CANONICAL_BUILDER.md).

Only APPROVED mapping rules that pass deterministic validation may be used. Transformations are explicit and versioned. Entity relationships must be declared; V0.2 only constructs row-overlap relationships between definitions derived from the same source CSV.

## Current output artifacts

The audit generates data_audit_report.md, dataset_manifest.json, column_coverage.csv, json_structure_paths.csv, source_inventory.json, and mapping_review_queue.csv. The builder generates canonical_bundle.json only after successful canonical integrity validation, together with build_report.json. Failed builds produce a report and no canonical bundle.

## Acceptance boundary

Engineering fixtures test source preservation, mapping approval, stale hashes, explicit grouping, field conflicts, row-overlap linking, and canonical referential integrity. These tests are not scientific validation on the user's real corpus. Full end-to-end scientific acceptance remains reserved for V1.0.
