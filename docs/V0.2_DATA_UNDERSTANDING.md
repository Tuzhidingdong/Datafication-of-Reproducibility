# V0.2 — Data Understanding Engine

## Purpose

V0.2 prepares evidence for a human-approved canonical representation without silently deciding what a row, JSON object, field, or reported value means scientifically.

## Implemented foundation

- CSV row-shape checks distinguish short rows, long rows, and consistent rows.
- Nested JSON profiling records bounded structural paths, JSON value types, and list-length ranges; raw source text values are not copied into the profile.
- A deterministic source inventory assigns stable IDs from source hash plus locator.
- A mapping review queue exposes CSV columns and observed JSON structural paths as UNRESOLVED; it does not guess canonical field meanings.
- A canonical research bundle schema defines Study, System, Condition, Experiment, Observation, Comparison, and Evidence entities.
- A runtime validator checks canonical required fields, duplicate IDs, cross-entity references, selected relationship constraints, missingness vocabulary, and evidence locators.
- A mapping-plan schema and validator check source-inventory identity, source references, mapping status, canonical targets, explicit transformations, approval metadata, and duplicate approved targets.
- A canonical build specification declares entity grain, grouping keys, mapped fields, JSON record selectors, and relationship matching mode.
- The deterministic builder consumes only validated APPROVED mappings from CSV and JSON, preserves raw-value provenance with concrete locators, creates stable IDs, supports explicit same-source record links and cross-file field-equality joins, and validates the canonical bundle before writing it.
- Relationship diagnostics report exact-payload duplicate candidates and unreferenced entities without merging or deleting anything.

## Canonical entity model

See Canonical research data model (CANONICAL_DATA_MODEL.md) for definitions, relationship rules, endpoint separation, missingness, provenance, and validation boundaries.

The model does not assume one input row or JSON object equals one experiment or replicate. Entity granularity is explicitly declared through SOURCE_ROW or GROUP_BY_FIELDS rules. Grouped field conflicts cause a build failure; the builder does not select an arbitrary value or average records.

## Mapping and construction contracts

See Mapping contract (MAPPING_CONTRACT.md) and Canonical Builder contract (CANONICAL_BUILDER.md).

Only APPROVED mapping rules that pass deterministic validation may be used. JSON record selection uses an explicit RFC 6901 Pointer template with array wildcard *. Field extraction uses the source inventory's structural path pattern relative to each selected record. Cross-file links require exact equality between two explicitly mapped fields. No implicit identifier or unit normalization is performed.

## Current output artifacts

The audit generates data_audit_report.md, dataset_manifest.json, column_coverage.csv, json_structure_paths.csv, source_inventory.json, and mapping_review_queue.csv. The builder generates canonical_bundle.json only after successful canonical integrity validation, together with build_report.json. Failed builds produce a report and no canonical bundle. The standalone diagnose-bundle command emits relationship_diagnostics.json.

## Acceptance boundary

Engineering fixtures test source preservation, mapping approval, stale hashes, explicit CSV/JSON selectors, multiple-value rejection, cross-file equality joins, ambiguous/missing join handling, field conflicts, and non-destructive diagnostics. These tests are not scientific validation on the user's real corpus. Full end-to-end scientific acceptance remains reserved for V1.0.
