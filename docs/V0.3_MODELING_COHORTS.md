# V0.3 — Endpoint-specific modelling cohorts

## Purpose and boundary

The first V0.3 component converts a human-approved modelling task and a structurally valid canonical bundle into an endpoint-specific cohort with deterministic study-level partitions. It does **not** fit models, tune hyperparameters, infer scientific mappings, adjudicate reconciliation issues, or establish scientific validity.

A modelling cohort is task-specific. The same canonical bundle can produce different cohorts for different outcomes, endpoint definitions, feature sets, or unit requirements. There is no global complete-case table.

## Task contract

Create a task file based on `schemas/modeling_task.schema.json`. It must explicitly define:

- `target_id` and the exact `endpoint_definition` string. No fuzzy endpoint matching is performed.
- Outcome type, selected value field (`raw_value` or `normalized_value`), and exact unit. Unit conversion is not performed here.
- Each feature's stable `feature_id`, exact canonical `Condition.condition_type`, selected value field, value type, and exact expected unit.
- A study-level split strategy: deterministic grouped holdout with train/validation/test fractions and a seed, or explicit validation/test Study IDs.

The task is an analysis contract, not a place to invent mappings. Feature bindings must already have been reviewed against the canonical bundle and approved domain mapping. A raw value and a normalized value are never silently substituted.

## Eligibility and grain

The builder:

1. Requires the canonical bundle to pass structural and referential-integrity validation.
2. Selects only observations whose `target_id` and `endpoint_definition` exactly match the task.
3. Accepts only `value_state = REPORTED` and a valid scalar matching the requested outcome type.
4. Requires the exact requested outcome unit.
5. Resolves every feature through the Experiment's explicit `condition_ids` and exact `condition_type`.
6. Requires exactly one linked Condition for each feature binding, a `REPORTED` value, the expected scalar type, and an exact unit match.

Missing, ambiguous, multiply linked, non-reported, invalid, or wrong-unit features exclude that Observation with a recorded reason. The builder does not impute, convert units, infer condition equivalence, choose among multiple matching conditions, or average observations. Multiple Observation records remain separate rows; their independence or replicate meaning is not inferred.

Only exact scalar values are admitted. Numeric strings are not silently parsed as numbers. Use an explicitly approved upstream transformation and canonical normalized field when conversion or parsing is scientifically justified.

## Study-aware splitting

The grouping unit is canonical `study_id`, not Observation, Experiment, DOI text inferred from a title, or CSV row. All eligible observations from a Study receive the same split.

- `GROUPED_HOLDOUT`: sort Study IDs by a deterministic SHA-256 ordering derived from the seed and Study ID, then allocate whole studies according to the declared fractions. Each of train, validation, and test must contain at least one Study; at least three eligible studies are required.
- `EXPLICIT_STUDIES`: the task names validation and test Study IDs; remaining eligible studies become train. Overlap and unknown/ineligible IDs are rejected.

This is a grouping safeguard, not proof that the studies are statistically independent. If multiple Study records represent the same underlying research programme or shared data, that dependency must be resolved in the canonical representation or the explicit split plan.

## Command

After G2 approval, run:

```bash
dor build-cohort --bundle canonical_bundle.json --task modeling_task.json --out-dir 04_modeling/cohort
```

The output directory must be new or empty. Inputs are read-only and are hash-checked before/after reading.

## Output package

- `modeling_cohort.csv`: one row per eligible Observation, with stable IDs, Study/System/Experiment/Observation references, exact endpoint, outcome, split, and explicit feature columns.
- `cohort_report.json`: exact task scope, hashes, inclusion count, exclusions by reason, feature coverage, and split counts.
- `split_manifest.json`: Study-to-split mapping, Observation IDs by split, and a deterministic zero-overlap check.
- `modeling_cohort_manifest.json`: task and bundle hashes plus artifact inventory.

Inspect the exclusion list and split manifest before fitting any model. A zero-overlap check only means the same canonical Study ID was not placed in multiple partitions; it does not rule out duplicate literature records or hidden inter-study dependencies.

## Review and scientific safeguards

Reconciliation must be completed before analysis planning: review endpoint gaps/variants, repeated-observation grain, same-replicate conflicts, and evidence extraction disagreements. The cohort builder does not apply reconciliation decisions automatically in this initial V0.3 increment. Do not use affected observations until the human review outcome and analysis eligibility have been explicitly decided at G2.

The output is a prepared dataset, not a trained model, prediction, metric, discovered interaction, or mechanism claim. After cohort review, the initial deterministic baseline engine is available; see [V0.3 Baseline Model Engine](V0.3_BASELINE_MODELS.md). Nested Study-level reproducibility evaluation and heuristic feature-space support diagnostics are now implemented; see [V0.3 Reproducibility Evaluation](V0.3_REPRODUCIBILITY_EVALUATION.md). Initial numeric pairwise interaction screening, repeated-seed split-sensitivity assessment, and descriptive numeric-pair response surfaces are implemented in V0.4; see the corresponding V0.4 method documents. Categorical interaction models, inferential multiplicity control, alternative model/encoding families, and mechanism interpretation remain future work.

## Engineering acceptance

Synthetic unit tests cover exact endpoint separation, missingness, explicit feature binding, ambiguous/multiple conditions, exact units, multiple observations without aggregation, deterministic splits, group leakage prevention, invalid split definitions, source immutability, and output-directory protection. These tests do not constitute real-corpus scientific acceptance; that remains reserved for V1.0.
