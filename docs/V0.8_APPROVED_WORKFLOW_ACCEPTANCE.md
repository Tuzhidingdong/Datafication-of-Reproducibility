# V0.8 — Fully approved workflow acceptance and cross-artifact lineage

## Acceptance target

The prior synthetic project test exercised the complete CLI pipeline but used the V0.7 legacy bypass. V0.8 upgrades that acceptance fixture to make actual human-decision records at every gate. Gated commands receive the same project workflow ledger, and no command is permitted to use \`--allow-untracked-legacy\`.

## Five-gate execution

| Gate | Synthetic acceptance point | Exact artifact relationship checks |
|---|---|---|
| G0 | After source audit | Dataset manifest and source inventory are both bound to the ledger |
| G1 | After mapping validation and build-spec preparation | Inventory matches G0; mapping plan and build spec reference the exact inventory and mapping-plan hashes; mapping validation is recomputed and compared |
| G2 | After canonical construction, canonical validation, reconciliation, and task preparation | Validation report passes; reconciliation points to the exact bundle hash; bundle build provenance matches current G1 mapping, inventory, and build-spec hashes |
| G3 | After interaction discovery, repeated-seed robustness, complete candidate selection, and mechanism-plan preparation | Interaction/robustness report hashes match the two manifests; both manifests reference the exact G2-approved task and identical cohort/split hashes; report candidate ID sets agree; mechanism plan matches the single selected ID |
| G4 | After package plan and reviewed result preparation | Exact publication plan and reviewed model report are bound |

The synthetic reviewer identity is a test fixture, not a real person and not an authentication mechanism.

## Negative acceptance tests

1. **Changed G1 decision:** copy the completed ledger, prepare a revised mapping plan and a build specification whose mapping hash is consistent with it, and append a new G1 approval. The old G2, G3, and G4 decisions must become \`BLOCKED_UPSTREAM\`. Running \`dor build-cohort\` against that copied ledger must fail before it creates an output directory.
2. **Substituted Canonical Bundle:** pass an alternate bundle path to \`dor build-cohort\` while using the original approved ledger. The command must reject the non-approved path before creating an output directory.
3. **Cross-artifact mismatch:** unit tests reject a build specification bound to another mapping plan, a reconciliation report bound to another bundle, and a robustness manifest generated from a different modeling task.
4. **No legacy bypass:** the end-to-end fixture inspects every gated CLI call and requires \`--workflow-ledger\`; it fails if \`--allow-untracked-legacy\` appears.

## Runtime lineage rules

- G1 requires the exact same source-inventory path and hash recorded at G0. Its mapping validation is deterministically recomputed with the exact plan and inventory. The build specification must reference both the approved plan hash and inventory hash.
- G2 requires a successful canonical-validation report and a reconciliation report referencing the approved canonical bundle hash. The bundle's build_provenance must match the latest G1-approved mapping-plan, inventory, and build-spec hashes. Thus a remapping requires a new canonical build before G2 can be re-approved.
- G3 requires the interaction discovery report and repeated-seed robustness report, their corresponding manifests, and a schema 1.1 selection record. Each manifest's task hash must match the G2-approved modeling task. Both manifests must contain the same cohort, cohort-report, split-manifest, and cohort-manifest hashes. The output hashes must match the exact reports, and the two catalogues must contain the same interaction IDs.
- A G3 mechanism plan remains optional only when the user selects no candidate. When present, its task and interaction IDs must match the approved G3 selection.

The checks are repeated when the ledger is read. If an artifact itself has changed, the runtime preserves the V0.7 behavior of reporting \`STALE_ARTIFACT\`; semantic checks are skipped for that stale event so that the ledger can still report the invalidated state rather than hiding it behind a JSON parse error.

## Validation boundary

The fixture runs only temporary synthetic data through the real \`dor\` CLI entry point. It demonstrates file-level and cross-file workflow enforcement, not physical chemistry, scientific truth, reviewer identity authentication, or resistance to an administrator who can rewrite files and recompute all hashes. No project-specific real research corpus is loaded. Full scientific acceptance remains reserved for V1.0.
