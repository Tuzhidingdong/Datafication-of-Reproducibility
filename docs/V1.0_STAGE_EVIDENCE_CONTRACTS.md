# V1.0 Stage Evidence Contracts

## Contract registry

The fixed registry is implemented in `runtime/src/dor/stage_contracts.py` and described in `schemas/v1_stage_evidence_contract.schema.json`. Its version is `1.0`; it covers the exact eight stages in the acceptance protocol. The registry is implementation-owned: an acceptance record cannot redefine required evidence types or weaken a check.

| Stage | Required evidence types |
|---|---|
| `source_selection` | `source_selection_manifest`, `source_inventory` |
| `source_integrity` | `run_manifest` |
| `extraction_review` | `extraction_review_record` |
| `semantic_mapping` | `mapping_plan` |
| `canonical_reconciliation` | `canonical_bundle`, `reconciliation_report`, `reconciliation_decisions` |
| `cohort_feasibility` | `modeling_task`, `cohort_report`, `split_manifest`, `modeling_cohort_manifest`, `modeling_cohort_csv` |
| `modeling_validation` | `model_report`, `model_artifact`, `modeling_run_manifest`, `reproducibility_evaluation`, `reproducibility_evaluation_manifest` |
| `publication_handoff` | `publication_package_manifest`, `publication_integrity_report` |

## Structural and relational rules

- Source selection uses `schemas/v1_source_selection_manifest.schema.json` and its example template. `selected_sources` and `excluded_sources` must form a disjoint, exact partition of the Run's initialized source snapshot. Both groups carry source ID, role, exact path, and SHA-256; every exclusion also requires a reason. The source inventory may reference selected sources only. Inventory entries must carry explicit inventory IDs, source hashes, file labels, locator types, and locators; duplicate IDs and malformed hashes are rejected.
- The run manifest must match the acceptance run/project identity. Run Manager verification remains the authority for the event chain and initialized source snapshot.
- Extraction review uses a DOR-owned review-record contract rather than assuming a particular upstream extraction tool's output schema. It requires source-hash bindings, exact locators, per-locator review states, and a named human decision.
- Mapping plans must bind to the source-inventory hash. A rule still marked `PROPOSED` blocks a passed mapping stage. An `APPROVED` rule must explicitly declare target entity/field, transformation parameters, and human review metadata. `UNRESOLVED` remains visible; it is not silently converted to a mapping.
- Canonical validation reuses the existing canonical graph validator, including ID uniqueness and cross-entity references. The canonical bundle must bind the exact accepted mapping-plan and source-inventory hashes. Reconciliation must bind to the exact canonical bundle SHA-256 and report its issue count consistently. Human reconciliation decisions are revalidated against the exact report and bundle; every CRITICAL/REVIEW_REQUIRED issue must have an explicit decision and cannot remain unresolved for PASS.
- Cohort and split evidence must identify the endpoint/task and explicit Study assignments. The Study ID set must match the acceptance snapshot, and train/validation/test must be non-empty and non-overlapping.
- Model evidence must include the model report, serialized model artifact, baseline run manifest, nested Study-grouped evaluation report, and its manifest. Task/model identities, model/report hashes, cohort/split input hashes, model split assignments, outer held-out fold coverage, and per-Study results are checked. Each Study must be held out exactly once; training/test and inner-training/validation groups must not overlap. The evaluation remains NOT_CALIBRATED; this contract does not invent an acceptable MAE/RMSE or other scientific performance threshold.
- Publication evidence must point to the exact `package_manifest.json` in the package root and a separately stored integrity report. The validator independently re-runs the publication package auditor against that directory, recomputes guide and artifact hashes, checks missing/extra files and path safety, and compares the fresh audit result with the stored report. The manifest's completeness status and unresolved-items list must be derived from its artifact statuses; `valid=true` alone is never sufficient.
- Publication handoff must bind the package to the same run/project, hash-bind the Writing Skill guide, and include an integrity report with no errors.

## Deliberate boundaries

This registry checks evidence shape, provenance bindings, and deterministic relationships. It does not decide whether an extraction is scientifically faithful, whether a mapping is domain-appropriate, whether a unit conversion is scientifically justified, whether a cohort is scientifically sufficient, or whether model performance is useful. Those remain explicit human decisions and domain-specific approved plans.

The `extraction_review_record` is a DOR contract, not a claim about the output format of `chem-literature` or any other upstream parser. An adapter may produce this record while preserving the original extraction artifacts and their locators.


## Runtime integration

A PASS record's evidence descriptors declare `artifact_type` alongside the Run-bound artifact ID, path, and hash. The acceptance validator opens those exact JSON files and executes the fixed registry automatically. The caller cannot replace a required artifact or satisfy a stage by selecting a different JSON Pointer. Source selection and exclusions must partition the acceptance source snapshot exactly; the mapping plan is hash-bound to the selected inventory; the canonical graph's Study IDs must match the declared scope; Cohort splits must cover the endpoint-eligible Study set; model split assignments must match the accepted split; and publication integrity must report a valid package. Generic JSON Pointer assertions remain supplemental only.


The Cohort CSV is the only non-JSON evidence type in this V1.0 contract. Its bytes are verified by the Run-bound SHA-256; the Cohort manifest must repeat the exact CSV hash. It is not parsed as JSON. The modeling task is an explicit task artifact and is not inferred from data columns or output labels.


The source-selection manifest's required shape and explicit exclusion rationale are defined in `schemas/v1_source_selection_manifest.schema.json` and `templates/v1_source_selection_manifest.example.json`. The Run snapshot is the boundary for what was made available; it is not an instruction to include every available file in the scientific analysis.


## Adversarial contract regression checks

The dedicated `runtime/tests/test_stage_contracts.py` suite is run separately in CI as well as in the complete runtime suite. It includes adversarial cases for:

- extraction review must inherit the exact selected-source subset from the preceding source-selection stage; excluded sources must not be included in its hash set or reviewed locators;
- a rejected or follow-up extraction decision cannot support a PASS stage;
- a Run Manifest cannot conceal duplicate source artifact IDs behind dictionary construction;
- malformed non-object stage evidence entries fail closed rather than crashing the validator;
- source-selection exact partitioning, selected-only inventory, cross-stage task/Study/hash bindings, nested Study leakage, and independently recomputed publication package integrity.

All adversarial fixtures are synthetic and use temporary paths. The suite does not open or process the user's real research corpus.


### Model-task exactness hardening

A model PASS now requires exact agreement between the accepted `modeling_task`, `model_report`, and serialized `model_artifact`: task/target/endpoint IDs, outcome type, outcome value field, exact outcome unit (including null), and ordered feature-binding definitions. The selected model type and primary selection metric must also agree between the report and serialized artifact. A matching task ID alone is not sufficient. The report schema now requires explicit outcome value field and unit keys so absence cannot be confused with an intentional null unit.


### Ambiguous source locators and reconciliation issue identity

The source inventory uses the explicit file-label/hash pair available in its current schema. If two distinct selected source IDs have the same basename and SHA-256, that pair cannot distinguish their identity; the inventory stage now rejects this ambiguity rather than silently assigning an item to either source. Reconciliation reports must also use unique, non-empty string issue IDs and a true integer issue count. Malformed issue IDs are rejected before decision lookup, and malformed decision inputs produce a blocking validation issue rather than an uncaught runtime exception.


- The publication package `source_hashes` map must equal the exact source-ID-to-SHA-256 mapping of the previously accepted `selected_sources` list. A package cannot claim an unselected source, omit a selected source, substitute a stale digest, or use a filename label as a substitute for a Run source ID.
