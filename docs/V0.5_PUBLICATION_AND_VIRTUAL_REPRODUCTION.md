# V0.5 — Publication package assembly and virtual reproduction

## Scope

V0.5 adds two deterministic hand-off operations:

1. Assemble a curated, self-contained publication package from an explicit artifact plan, with package-relative paths and SHA-256 checks.
2. Query a selected, hash-verified baseline model for a fully specified feature condition set, while exposing marginal training-domain warnings and uncalibrated uncertainty.

This increment does not generate scientific claims, figures, tables, references, missing data, or manuscript prose. The user/Agent must prepare an artifact plan and mark each entry according to what actually exists.

## A. Publication package assembly

### Explicit plan

For a formal DoR Run, choose **templates/publication_package_plan.example.json** (or the matching controlled single-Study template) as the immutable `publication_plan_template` before Run initialization. Do not edit it into a run-specific final plan outside the Run. After G3, Worker review, and human disposition, the Run's `publication_plan_preparation` stage creates the final `publication_plan` inside the Run and binds every file to its exact Run Artifact ID/path. The final plan is validated against **schemas/publication_package_plan.schema.json** and the active Run before G4.

The plan contains:

- stable project/run/package IDs;
- optional domain-profile reference and optional source hashes;
- one entry per intended artifact;
- package-relative destination path;
- workspace-relative source path for files that actually exist;
- exact `source_artifact_id` for every sourced file in a formal Run, binding the package entry to the Run Artifact Manifest;
- exact artifact type, description, status, linked record IDs, and manuscript sections.

Each artifact is a file. If a directory contains multiple required files, declare each file separately. The builder does not recursively search the workspace and does not infer artifact roles from file names.

Statuses have operational consequences:

| Status | Required source | Package behaviour |
|---|---|---|
| complete | Required | Copy file and record SHA-256 |
| partial | Required | Copy file, retain partial status |
| requires_review | Optional | Copy/hash if supplied; otherwise preserve unresolved path/status |
| not_generated | Forbidden | Retain planned path/status without creating a placeholder |
| not_applicable | Forbidden | Retain status; do not create a placeholder |

Complete and partial entries without an existing source file fail. Source files must resolve within workspace-root; absolute paths, traversal, and symlinks escaping the workspace are rejected. The builder copies declared files only and verifies source and destination hashes. It never modifies inputs.

The output directory must be new or empty. A writing guide is copied to README_FOR_WRITING_SKILL.md; by default the bundled template is used. A run-specific guide can be supplied with writing_guide_source relative to the workspace root.

### Build command

The package builder is G4-gated. For a formal Run, use the Run Manager path only: the final plan must pass `dor validate-publication-plan`, then the user must approve the exact plan, validation report, and every sourced Run Artifact at G4. Do not use the legacy untracked-workflow override for a research Run. Run Manager invokes the command with both the exact plan and validation report:

~~~bash
dor validate-publication-plan --plan <run_root>/10_publication/publication_package_plan.json --manifest <run_root>/run_manifest.json --out <run_root>/10_publication/publication_plan_validation.json

After the user has reviewed and approved the exact final scope, record G4. Bind the final plan, validation report, Worker/human review set, Cohort review set, and every additional source row listed in the validation report:

dor gate-record --workflow-ledger <run_root>/workflow_gate_ledger.jsonl --gate G4 --decision APPROVE --reviewer "<reviewer>" --rationale "<approved final publication scope>" --artifact publication_plan=<run_root>/10_publication/publication_package_plan.json --artifact publication_plan_validation=<run_root>/10_publication/publication_plan_validation.json --artifact worker_review_output=<run_root>/worker_staging/independent_result_review/review.json --artifact reviewed_findings=<run_root>/09_review/reviewed_findings.json --artifact model_artifact=<run_root>/06_modeling/baseline/model_artifact.json --artifact model_report=<run_root>/06_modeling/baseline/model_report.json --artifact reproducibility_evaluation=<run_root>/06_modeling/reproducibility/reproducibility_evaluation.json --artifact interaction_report=<run_root>/06_modeling/interactions/interaction_discovery_report.json --artifact robustness_report=<run_root>/06_modeling/interaction_robustness/interaction_robustness_report.json --artifact interaction_selection=<run_root>/07_review/interaction_selection.json --artifact virtual_prediction=<run_root>/08_virtual_reproduction/virtual_prediction.json --artifact cohort_review_record=<run_root>/05_modeling/cohort/cohort_review_record.json --artifact cohort_review_validation=<run_root>/05_modeling/cohort/cohort_review_validation.json

# Also bind every additional source Artifact listed in publication_plan_validation.source_artifacts
# (for example optional mechanism/response-surface outputs); omit not_generated entries.

dor build-publication-package --plan <run_root>/10_publication/publication_package_plan.json --validation <run_root>/10_publication/publication_plan_validation.json --workspace-root <run_root> --out-dir <run_root>/10_publication/package --workflow-ledger <run_root>/workflow_gate_ledger.jsonl
~~~

Outputs:

- README_FOR_WRITING_SKILL.md
- package_manifest.json

Plus only the declared artifact files. The manifest records package-relative paths, artifact states, hashes for copied files, linked IDs, manuscript sections, source hashes, creation time, and overall completeness. It does not publish absolute local source paths.

### Integrity audit

~~~bash
dor audit-publication-package \
  --package-dir 06_publication/package \
  --out 06_publication/package_integrity_report.json
~~~

The audit checks the guide checksum, artifact IDs and paths, required/missing files, artifact status consistency, copied-file SHA-256, and unindexed files. The audit report should be stored outside the package being audited.

A successful integrity audit means the package is internally consistent; it does not mean that all science is complete or publication-ready. The completeness object and per-artifact status remain authoritative for missing and review-required material.

## B. Virtual condition prediction

### Input contract

Use **templates/virtual_reproduction_query.example.json** and **schemas/virtual_reproduction_query.schema.json**.

A query must give the exact task_id, target_id, endpoint_definition, and complete feature set keyed by canonical feature_id.

Each feature entry contains exactly value and unit. Numeric values must be finite JSON numbers, not numeric strings. Categorical values must be non-empty strings. Units must exactly match the feature binding's expected_unit; no implicit unit conversion is performed. Missing and extra feature IDs are rejected. The prediction applies only to the specific endpoint and model task, not an entire system or category.

### Command

The input model directory must be the exact output from dor fit-baselines, including model_artifact.json, model_report.json, and modeling_run_manifest.json.

~~~bash
dor predict-virtual-condition \
  --model-run-dir 04_modeling/baseline_run \
  --query virtual_reproduction_query.json \
  --out 06_publication/virtual_prediction.json
~~~

The command verifies the model artifact and model report against the run manifest hashes, and checks task/model identity plus disjoint training and held-out test Observation IDs. It applies the serialized selected mean/Ridge/majority/Naive-Bayes model; it does not retrain or refit anything.

### Training-domain record

V0.5 extends newly generated model artifacts with training_feature_domain, computed from the final fitting population (train + validation only):

- numeric feature minimum and maximum;
- categorical values present in the fitting population;
- exact expected unit and count.

Held-out test observations are excluded. Existing legacy model artifacts without this field remain readable, but their feature support is reported as not assessable.

A numeric value outside its recorded marginal range is labelled OUTSIDE_TRAINING_RANGE; an unseen categorical value is UNKNOWN_CATEGORY. The model still returns the mathematical scenario estimate, but the report marks it as EXTRAPOLATIVE_OR_UNKNOWN_CATEGORY_SCENARIO. This output is a warning-bearing sensitivity result, not a supported prediction.

Even values within every marginal range may lie outside observed joint multivariable combinations. V0.5 does not calculate nearest training neighbours because raw training rows are not embedded in the model artifact. It therefore reports MARGINAL_DOMAIN_ONLY and nearest_training_observation = NOT_COMPUTED rather than inventing a proximity score.

### Mandatory interpretation boundary

Every virtual result includes:

- uncertainty_status = NOT_CALIBRATED;
- no confidence interval, prediction interval, or calibrated probability;
- marginal feature support checks and out-of-range/unknown-category warnings;
- training and held-out test Observation IDs;
- test_set_used_for_fit_or_selection = false;
- explicit statement that this is a model-based scenario estimate, not a direct observation or a result from an independently executed specialist simulation.

A virtual estimate does not prove experimental reproducibility, causal effect, or mechanism. It must not be written as a measured result. Before using it to propose an experiment, examine cross-Study validation, support diagnostics, endpoint compatibility, and missing physical-state variables. A prediction outside its recorded marginal domain must never be presented as interpolation.

## Engineering acceptance

Synthetic tests cover package creation, hash verification, tamper detection, traversal rejection, overwrite protection, selected-model prediction, exact unit and feature matching, out-of-range values, unknown categories, stale-model rejection, and output protection. CI is an engineering test only. Full scientific acceptance on the real literature corpus remains reserved for V1.0.


### Symbolic-link rejection

The package auditor now rejects symbolic links anywhere under the package root, including directory links that a normal recursive file listing might not traverse. The package manifest itself must be a regular file, and the Writing Skill guide cannot be a symbolic link. This prevents an apparently clean package from containing a pointer to unindexed content outside the package or to mutable files elsewhere in the workspace.
