# V0.9 Run Manager: project runs, artifact lineage, and safe recovery

## Purpose and boundary

V0.9 adds a deterministic run-management layer above the existing scientific Runtime. It records stage attempts, exact input/output files, hashes, Worker task metadata, and conservative resume decisions.

It does not replace the G0-G4 approval ledger. A run event is execution provenance, not scientific approval. No Run Manager command creates an approval event, interprets scientific meaning, launches a Worker, or executes a planned stage.

## Explicit run plan

Before creating a run, the Supervisor must prepare a complete run_plan.json with:

- explicit protected source_roots and source_artifacts (absolute paths);
- all workflow stages decomposed before execution;
- each stage's stable stage_id, executor (local, worker, or manual), direct dependencies, exact input artifact IDs, exact output artifact IDs/paths, and optional required G0-G4 gate;
- Worker-only outputs under worker_staging/<stage_id>/.

The Runtime does not crawl the workspace, infer artifact roles from filenames, create missing input declarations, or guess dependencies. A derived artifact may be consumed only by a stage that explicitly declares its producer as a dependency.

Use dor run-init --plan run_plan.json --run-root path/to/new/run to create an independent run workspace. The command copies the exact plan to run_plan.json, hashes every source artifact, and initializes run_manifest.json and run_events.jsonl. The run root must be new or empty and must not be nested inside, or contain, a protected source root.

## Stage lifecycle and immutable event history

Record every stage attempt with dor run-stage-record:

1. RUNNING immediately before the explicitly planned local/manual action or after Worker authorization and before external dispatch.
2. SUCCEEDED only after all declared outputs exist and input hashes remain unchanged.
3. FAILED with a non-empty reason when the attempt fails.

Each event contains the run/stage/attempt IDs, actor/producer metadata, timestamp, input/output file paths and SHA-256 hashes, and a previous-event hash. run_events.jsonl is an append-only hash chain. A failed stage can be retried as a new attempt. A previously RUNNING attempt is never assumed to have stopped; inspect the external process and pass --confirm-abandoned before recording a replacement attempt.

A source artifact changing after run initialization requires a new run. Do not rebase an existing run onto changed raw data.

## Worker dispatch contract

Worker stages are declared in advance with executor: worker. Before using the existing Antigravity-to-OpenCode Worker Manager, the Supervisor must show the user the exact role, provider, model, active project root, input artifact paths/hashes, permitted staging outputs, and task constraints. Wait for explicit user authorization.

After authorization, call dor run-worker-authorize. It records who authorized the dispatch and emits a bounded task packet. This command does not start a Worker. The actual Worker Manager invocation remains an external host action and must use the displayed role/model/project and declared inputs.

Worker output paths must be new files under worker_staging/<stage_id>/. A Worker cannot overwrite source files, run manifests, event ledgers, G0-G4 ledgers, or approved scientific artifacts. Worker stage outputs cannot be declared as normal derived outputs. A separate manual review/promotion stage must consume staging outputs and write accepted derived artifacts.

After the Worker Manager reports completion, record SUCCEEDED or FAILED, and include job/session IDs and token-usage fields only when actually reported. Missing token data stays missing; do not record zero as a guess. The task's completion is not G0-G4 approval.

The authorizer and reviewer strings are self-declared provenance metadata, not authenticated identities or cryptographic signatures.

## Recovery and selective invalidation

Use these commands when resuming:

- dor run-verify --manifest run_manifest.json checks the copied plan hash, source snapshots, and run-event hash chain.
- dor run-status --manifest run_manifest.json summarizes current stage actions.
- dor run-resume-plan --manifest run_manifest.json --out resume_plan.json calculates the complete recovery plan without running anything.

Actions include:

- REUSE: the stage's exact input/output hashes and dependency states are current.
- READY_TO_RUN: inputs/dependencies are ready and no valid completed attempt exists.
- REBUILD_REQUIRED: this stage's inputs or outputs changed or disappeared.
- INVALIDATED_BY_UPSTREAM: a completed stage depends on an upstream stage that is no longer reusable.
- RETRY_REQUIRED: the last recorded attempt failed.
- RUNNING_NEEDS_RECONCILIATION: a prior attempt was left running; process state must be checked.
- BLOCKED_GATE: its required G0-G4 approval is not currently valid.
- WAITING_FOR_DEPENDENCIES: an upstream stage must be completed or rebuilt first.

Invalidation propagates only through declared dependency edges. Independent stages remain reusable. A downstream stage is never treated as reusable merely because its own output file still exists.

The resume command is plan-only. The Supervisor reviews the plan and performs the actions in dependency order; it does not automatically retry failed work, start Workers, regenerate outputs, alter gate decisions, or approve a scientific result.

## Integrity and limitations

The run plan is copied and hash-bound at initialization. Source files are snapshotted and never written by the Run Manager. Derived outputs are tracked by explicit artifact ID and path. The run event ledger detects edits/reordering within the recorded chain, but like the existing gate ledger it is not a secure signature system: a party able to rewrite the entire ledger can recompute the chain.

V0.9 manages records and recovery decisions only. It does not yet provide process supervision, cancellation, automatic Worker Manager integration, automatic artifact promotion, or cross-machine execution. Do not infer that a Worker process is active or complete from a run event alone.


Worker task restrictions and staging paths are an explicit execution contract, not an operating-system sandbox. The host Worker Manager must still run with guarded permissions and a bounded project/workdir. The Runtime checks declared input hashes before/after a stage and rejects a successful completion if declared inputs changed; undeclared workspace writes cannot be detected because workspace crawling is intentionally disabled.


## Artifact manifest

The stage event ledger is the source of truth. Generate a read-only, regenerable artifact view at any time:

    dor run-artifacts --manifest run_manifest.json --out artifact_manifest.json

The report lists every declared source and derived artifact by stable ID, producer stage, path, expected SHA-256 from the source snapshot/latest successful stage event, current SHA-256, and status. The report is a projection, not an independent mutable database; regenerate it after new stage events. A missing/unrecorded file is not silently treated as a completed artifact.

## Safe rebuild rule

When a stage is marked REBUILD_REQUIRED, archive or move its previous output files out of their declared paths before starting a new attempt. The Runtime permits a new attempt only after its existing output paths are clear; it never overwrites old outputs. The stage's required gate decision hash is also bound to the attempt. A later reapproval of that gate invalidates the previous stage result even when its files have not changed.


## Stage decomposition rule

The example template illustrates a default path, not a license to combine unrelated operations into a single stage. For an actual research project, split every independently configured or independently reusable Runtime operation into its own stage: cohort construction, baseline fitting, nested reproducibility evaluation, interaction discovery, repeated-seed robustness, response-surface generation, virtual prediction, and publication assembly have different inputs and invalidation boundaries. Do not place cohort construction and model fitting in one stage merely for convenience.

Optional post-G3 mechanism work must be represented explicitly in the run plan chosen for that branch. Because candidate selection occurs during the run, do not fabricate a mechanism plan at initialization. If the optional branch cannot be declared honestly in the initial DAG, close the current run at G3 and create a separate follow-on run. Declare every required parent-run artifact as an explicit child-run source_artifact with exact path and hash, keep the parent run immutable, and record the parent run_id plus parent manifest SHA-256 in the project-level run index. V0.9 does not yet provide automatic parent/child run orchestration or a dedicated parent_run pointer.


## Initialization snapshot binding

Each run begins with a RUN_INITIALIZED event at sequence 1. It binds the exact run ID, project ID, plan path/hash, workspace, protected source roots/files/hashes, workflow-ledger path, and topological stage order. On every status, verify, resume, or Worker command, Runtime compares run_manifest.json against this immutable first event. A missing initialization event or any mismatch fails closed. This catches accidental manifest/source-snapshot edits; it is still not a cryptographic signature system because a party able to rewrite the entire manifest and event chain can recompute hashes.
