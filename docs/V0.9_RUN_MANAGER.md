# V0.9 Run Manager: project runs, artifact lineage, and safe recovery

## Purpose and boundary

V0.9 adds a deterministic Run Manager and a contract-bound local Stage Runner above the scientific Runtime. Together they record stage attempts, exact input/output files, hashes, Worker task metadata, and conservative resume decisions.

The Run Event Ledger does not replace the G0-G4 approval ledger. A Run event is execution provenance, not scientific approval. Run Manager commands never create Gate approvals or interpret scientific meaning. The Stage Runner executes only the exact local CLI subcommand and argv declared by the checked-in execution contract; it does not launch arbitrary shell commands or a Worker process.

## Explicit run plan

Before creating a run, the Supervisor must prepare a complete run_plan.json with:

- explicit protected source_roots and operational source_artifacts (absolute paths); optional provenance-only `acceptance_source_artifacts` are stored separately for post-Run V1.0 Acceptance and are never Stage inputs;
- all workflow stages decomposed before execution;
- each stage's stable stage_id, executor (local, worker, or manual), direct dependencies, exact input artifact IDs, exact output artifact IDs/paths, and optional required G0-G4 gate;
- Worker-only outputs under worker_staging/<stage_id>/.

The Runtime does not crawl the workspace, infer artifact roles from filenames, create missing input declarations, or guess dependencies. A derived artifact may be consumed only by a stage that explicitly declares its producer as a dependency.

Use dor run-init --plan run_plan.json --run-root path/to/new/run to create an independent run workspace. The command copies the exact plan to run_plan.json, hashes every source artifact, and initializes run_manifest.json and run_events.jsonl. The run root must be new or empty and must not be nested inside, or contain, a protected source root.

## Contract-bound local execution and stage lifecycle

For either supported Adapter route and either execution profile, use the contract-bound runner for local stages:

    dor run-resume-plan --manifest <run_root>/run_manifest.json
    dor run-advance --manifest <run_root>/run_manifest.json --max-local-stages 10

The Runtime resolves argv from the route/profile-specific `argv_template` in `stage_execution_contract.json`, resolves all paths from Run Artifact IDs, executes the allowed CLI command without a shell, and records RUNNING/SUCCEEDED/FAILED automatically. A successful attempt is recorded only when every declared output exists and can be hashed. It advances consecutive ready local stages and stops at the first human, Worker, Gate, unresolved-input, or failure boundary. It never auto-approves a Gate or starts a Worker. No per-stage argument JSON is required for supported adapter Run Plans. Custom/unbound Run Plans may use the explicit argv override only where permitted.

Do not use separate `run-stage-record` calls to simulate execution of a supported local stage. Use `run-stage-record` for operations completed outside the local Stage Runner: MANUAL tasks after their declared validation succeeds, and WORKER tasks after the host Worker Manager has returned a terminal result and the output contract is checked.

For those MANUAL/WORKER attempts, record:

1. RUNNING immediately before the manual operation, or after Worker authorization and before external dispatch.
2. SUCCEEDED only after all declared outputs exist and input hashes remain unchanged.
3. FAILED with a non-empty reason when the operation fails.
4. SKIPPED only when the stage declares an activation condition and the current activation value evaluates false. The event binds the exact activation-input artifact snapshot and a digest of the observed condition value; it creates no output artifact and no gate approval.

A stage may declare a generic condition in its Run Plan:
    
    "activation": {
      "artifact_id": "review_decision",
      "json_pointer": "/selected_ids",
      "operator": "array_non_empty"
    }

The activation artifact must also be a declared stage input. The producer must be currently reusable before the condition is evaluated. Supported operators are `exists`, `not_exists`, `array_non_empty`, `array_empty`, `boolean_true`, `boolean_false`, `equals`, and `not_equals`. JSON Pointer syntax is RFC 6901. The Runtime does not infer, generate, or modify activation inputs.

Each event contains the run/stage/attempt IDs, actor/producer metadata, timestamp, input/output file paths and SHA-256 hashes, and a previous-event hash. run_events.jsonl is an append-only hash chain. A failed stage can be retried as a new attempt. A previously RUNNING attempt is never assumed to have stopped; inspect the external process and pass --confirm-abandoned before recording a replacement attempt.

A source artifact changing after run initialization requires a new run. Do not rebase an existing run onto changed raw data.

For any stage with `required_gate`, a currently APPROVED status alone is insufficient. Before allowing the stage to start, Run Manager compares every artifact ID shared by the stage's declared inputs and the latest approved Gate event. The absolute/resolved file paths and SHA-256 digests must match exactly. Unshared stage inputs remain governed by their explicit Run Plan declarations and dependency snapshots. A mismatch is `BLOCKED_GATE`; this check is repeated at the dispatch boundary (`run-stage-record` RUNNING and `run-worker-authorize`) to close the gap between resume planning and actual execution.

## Worker dispatch contract

Worker stages are declared in advance with executor: worker. Before using the existing Antigravity-to-OpenCode Worker Manager, the Supervisor must show the user the exact role, provider, model, active project root, input artifact paths/hashes, permitted staging outputs, and task constraints. Wait for explicit user authorization.

After authorization, call dor run-worker-authorize. It records who authorized the dispatch and emits a bounded task packet. This command does not start a Worker. The actual Worker Manager invocation remains an external host action and must use the displayed role/model/project and declared inputs.

Worker output paths must be new files under worker_staging/<stage_id>/. A Worker cannot overwrite source files, run manifests, event ledgers, G0-G4 ledgers, or approved scientific artifacts. Worker stage outputs cannot be declared as normal derived outputs. A separate manual review/promotion stage must consume staging outputs and write accepted derived artifacts.

After the Worker Manager reports completion, record SUCCEEDED or FAILED, and include job/session IDs and token-usage fields only when actually reported. Missing token data stays missing; do not record zero as a guess. The task's completion is not G0-G4 approval.

The authorizer and reviewer strings are self-declared provenance metadata, not authenticated identities or cryptographic signatures.

## Recovery and selective invalidation

Use these commands when resuming:

- dor run-verify --manifest run_manifest.json checks the copied plan hash, source snapshots, and run-event hash chain.
- dor run-status --manifest run_manifest.json summarizes current stage actions.
- dor run-resume-plan --manifest run_manifest.json --out resume_plan.json calculates the complete recovery plan without running anything.

Actions include:

- REUSE: the stage's exact input/output hashes and dependency states are current.
- READY_TO_RUN: inputs/dependencies are ready and no valid completed attempt exists.
- REBUILD_REQUIRED: this stage's inputs/outputs changed or disappeared, or an earlier output file remains and must be archived before a previously skipped stage can be reactivated.
- INVALIDATED_BY_UPSTREAM: a completed stage depends on an upstream stage that is no longer reusable.
- RETRY_REQUIRED: the last recorded attempt failed.
- RUNNING_NEEDS_RECONCILIATION: a prior attempt was left running; process state must be checked.
- BLOCKED_GATE: its required G0-G4 approval is not currently valid.
- WAITING_FOR_DEPENDENCIES: an upstream stage must be completed or rebuilt first.
- WAITING_FOR_ACTIVATION_INPUT: the condition's declared producer is not currently reusable, or the input has not been created.
- SKIP_REQUIRED: the activation input is current and the declared condition evaluates false; record a SKIPPED event.
- SKIPPED: the condition remains false and the existing skip event is still bound to the current activation-input hash.
- A skipped stage has no outputs and does not satisfy another stage's artifact dependency. If its condition later becomes true, the stage becomes ready or requires rebuild/archiving of outputs from an earlier attempt.

Invalidation propagates only through declared dependency edges. Independent stages remain reusable. A downstream stage is never treated as reusable merely because its own output file still exists.

The `run-resume-plan` command is plan-only. The `run-advance` command executes only ready contract-bound local stages; it does not start Workers, perform manual review, regenerate unrelated outputs, alter Gate decisions, or approve a scientific result. A retry or rebuild still follows the dependency and archive decisions reported by the current resume plan.

## Integrity and limitations

The run plan is copied and hash-bound at initialization. Source files are snapshotted and never written by the Run Manager. Derived outputs are tracked by explicit artifact ID and path. The run event ledger detects edits/reordering within the recorded chain, but like the existing gate ledger it is not a secure signature system: a party able to rewrite the entire ledger can recompute the chain.

V0.9 provides plan validation, contract-bound local stage execution, stage provenance, and selective recovery. It does not provide external Worker process supervision/cancellation, automatic host Worker Manager dispatch, automatic promotion of Worker findings, or cross-machine execution. Do not infer that a Worker process is active or complete from a Run event alone.


Worker task restrictions and staging paths are an explicit execution contract, not an operating-system sandbox. The host Worker Manager must still run with guarded permissions and a bounded project/workdir. The Runtime checks declared input hashes before/after a stage and rejects a successful completion if declared inputs changed; undeclared workspace writes cannot be detected because workspace crawling is intentionally disabled.


## Artifact manifest

The stage event ledger is the source of truth. Generate a read-only, regenerable artifact view at any time:

    dor run-artifacts --manifest run_manifest.json --out artifact_manifest.json

The report lists operational sources and derived artifacts by stable ID, producer stage, path, expected SHA-256 from the source snapshot/latest successful stage event, current SHA-256, and status. Provenance-only `acceptance_source_artifacts` are listed in a separate field with their roles and independent hash status; they are not treated as computational Stage inputs. The report is a projection, not an independent mutable database; regenerate it after new stage events. A missing/unrecorded file is not silently treated as a completed artifact.

## Safe rebuild rule

When a stage is marked REBUILD_REQUIRED, archive or move its previous output files out of their declared paths before starting a new attempt. The Runtime permits a new attempt only after its existing output paths are clear; it never overwrites old outputs. The stage's required gate decision hash is also bound to the attempt. A later reapproval of that gate invalidates the previous stage result even when its files have not changed.


## Stage decomposition rule

The example template illustrates a default path, not a license to combine unrelated operations into a single stage. For an actual research project, split every independently configured or independently reusable Runtime operation into its own stage: cohort construction, baseline fitting, nested reproducibility evaluation, interaction discovery, repeated-seed robustness, response-surface generation, virtual prediction, and publication assembly have different inputs and invalidation boundaries. Do not place cohort construction and model fitting in one stage merely for convenience.

The two formal adapter Run Plans declare mechanism-plan preparation, response-surface generation, and mechanism-evidence bridging as conditional stages after candidate selection. The mechanism plan is declared as a stage output at initialization but is created only when a candidate is actually selected; this is not a fabricated placeholder. An empty selection produces explicit SKIPPED events without creating the optional files. If a genuinely new optional branch is not represented in the immutable parent plan, create a separate follow-on Run with the exact required parent artifacts declared as immutable source_artifacts. Record the parent run_id and manifest SHA-256 in the project-level Run index. V0.9 does not yet provide automatic parent/child Run orchestration or a dedicated parent_run pointer.


## Initialization snapshot binding

Each run begins with a RUN_INITIALIZED event at sequence 1. It binds the exact run ID, project ID, plan path/hash, workspace, protected source roots/files/hashes, workflow-ledger path, and topological stage order. On every status, verify, resume, or Worker command, Runtime compares run_manifest.json against this immutable first event. A missing initialization event or any mismatch fails closed. This catches accidental manifest/source-snapshot edits; it is still not a cryptographic signature system because a party able to rewrite the entire manifest and event chain can recompute hashes.


## Strict event integer types

The Runtime requires the JSON event `sequence` and every non-initialization event's `attempt` to be exact positive integers. Boolean values and floating-point values that compare equal to integers are rejected. This is a schema/type-integrity rule, in addition to the hash-chain and event-semantic checks. The unkeyed hash chain remains a consistency/tamper-evidence mechanism, not an authenticated signature system.
