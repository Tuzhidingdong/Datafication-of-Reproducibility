# V0.3 — Baseline model engine

## Scope

The baseline engine consumes only a completed, hash-verified modelling cohort and its exact task file. It trains deterministic baseline candidates, selects a candidate using the validation partition, refits the selected model on train plus validation, and evaluates it once on the held-out test partition.

This component is not an automatic model-family recommender, a causal discovery engine, a mechanism interpreter, or evidence that the chosen model is scientifically adequate. It supplies transparent reference performance and reproducible model artifacts for later evaluation.

## Supported baselines

### Numeric outcomes

- Mean baseline: predicts the mean outcome in the fitting partition.
- Ridge linear regression: numerical feature columns are standardized; categorical feature values are expanded into one-hot columns. All preprocessing parameters are fitted from the training partition only. A deterministic cyclic coordinate-descent solver fits ridge coefficients without an external ML dependency.
- Candidate ridge penalties are configured with `modeling.ridge_alphas` in the task file. Defaults are `[0.01, 0.1, 1, 10, 100]`.
- Candidate selection minimizes validation RMSE. A tie is resolved deterministically in favour of the simpler mean baseline, then the smaller ridge penalty.

Reported metrics: MAE, RMSE, and R². R² is null when the test set has fewer than two observations or its outcomes have zero variance.

### Categorical outcomes

- Majority-class baseline: predicts the most frequent training label; ties are resolved lexicographically.
- Mixed Naive Bayes: uses Gaussian likelihoods for numerical features and Laplace-smoothed categorical likelihoods for categorical features. Numeric feature scaling and all class-conditional statistics are fitted from the fitting partition.
- Candidate smoothing parameters are configured with `modeling.naive_bayes_smoothing`. Defaults are `[0.1, 1, 10]`; numeric variance floor is controlled by `modeling.naive_bayes_variance_floor`.

Candidate selection maximizes validation macro-F1. Ties are resolved in favour of the majority baseline, then the smaller smoothing parameter.

Reported metrics: accuracy, balanced accuracy, macro-F1, and a confusion matrix.

## Data-use protocol

1. Validate exact cohort/task IDs and hashes. The CSV, cohort report, and split manifest hashes must agree with the cohort manifest; the task file hash must be unchanged.
2. Recheck that every cohort row matches the exact task target/endpoint, its split matches the manifest, and every Study occurs in one partition only.
3. Fit candidate preprocessing and models on train only.
4. Compare candidate metrics on validation only and choose one candidate by the specified primary metric.
5. Refit the selected candidate on train plus validation.
6. Evaluate the selected model and its simple reference baseline on test. Test outcomes are not used for model or hyperparameter selection.
7. Record all fitting Study/Observation IDs and held-out test IDs.

There is no random row-level splitting, imputation, unit conversion, automatic feature selection, or silent removal of duplicate rows. Feature encoding is task-defined and deterministic. High-cardinality one-hot expansion above 500 encoded columns is refused by the Ridge path rather than silently truncated.

## Command

After G2 approval and review of the cohort report:

```bash
dor fit-baselines --cohort-dir 04_modeling/cohort --task modeling_task.json --out-dir 04_modeling/baseline_run
```

The output directory must be new or empty. The cohort and task inputs remain read-only.

## Output artifacts

- `model_report.json`: task identity, candidate validation metrics, selected candidate, and final test metrics.
- `model_artifact.json`: serialized model parameters and preprocessing state, feature contract, training IDs, and test IDs.
- `validation_model_comparison.csv`: candidate comparison using validation only.
- `test_predictions.csv`: held-out test observations, predictions, baseline predictions, and residuals/correctness.
- `modeling_run_manifest.json`: SHA-256 hashes for all inputs and generated outputs, split assignments, selected model, and fitting/evaluation protocol.

Machine-readable contracts are in `schemas/model_report.schema.json`, `schemas/model_artifact.schema.json`, and `schemas/modeling_run_manifest.schema.json`.

## Interpretation limits

A baseline winning validation does not mean it is scientifically sufficient. A Ridge model estimates linear associations on the task's explicitly supplied feature representation; it does not establish physical causality. Naive Bayes conditional-independence assumptions are often unrealistic for interacting experimental conditions, so it is included as a transparent reference, not a mechanistic model.

The held-out test metrics estimate performance only for the tested Study partition and endpoint definition. Applicability domain, between-study heterogeneity, uncertainty calibration, and prospective replication are later evaluation tasks. Do not select a model after inspecting the test metrics.

## Engineering acceptance

Synthetic tests cover numeric and categorical paths, validation-based selection, held-out test isolation, model artefact content, input hash validation, source immutability, and output-directory protection. They do not establish scientific validity on the real literature corpus; full acceptance remains reserved for V1.0.
