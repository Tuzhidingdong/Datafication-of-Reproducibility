# Canonical Builder Contract

## Purpose

The canonical builder converts a reviewed mapping plan into canonical research entities. It executes deterministic transformations only after mapping approval and requires a separate build specification for entity identity and relationships. It does not infer scientific grain from table shape.

## Three versioned inputs

1. source_inventory.json: source file hashes and structural field inventory created by dor audit.
2. mapping_plan.json: approved source-item to canonical-field rules.
3. canonical_build_spec.json: entity grouping, record selectors, and relationship declarations.

The build specification stores SHA-256 digests of the exact inventory and mapping plan files. Any edit to either file invalidates the build spec and requires regeneration/review.

## Entity grain

Each entity definition names a source file, source format, and grouping rule:

- SOURCE_ROW: one entity per selected source record. For CSV, a record is a data row; for JSON, a record is an object selected by the JSON Pointer template. This is an explicit declaration, not a default.
- GROUP_BY_FIELDS: one entity per unique combination of the listed inventory field IDs. Every grouping key must resolve to exactly one non-empty scalar value for each selected record.

Use keys that reflect the scientific identity of that entity. For example, a Study may group by DOI, while a System may group by DOI plus a system identifier, and an Experiment may group by an explicitly reviewed experiment/protocol key. The builder does not decide those keys for the user.

## JSON record and field selectors

A JSON entity definition declares source_format: json and record_selector, an RFC 6901 JSON Pointer template. The * token explicitly fans out over an array. For example:

    /papers/*/experiments/*

Every selected value must be an object. A mapping rule points to a source inventory item whose locator is the bounded structural path emitted by the audit profiler, for example $['papers'][]['experiments'][]['temperature']. The builder checks that the structural path lies beneath the declared record selector, then resolves the relative path within each selected object. It records the resulting concrete JSON Pointer, including actual array indices.

A selected object's mapped path must resolve to zero or one value. Multiple matches mean the entity record is too coarse; define a deeper record_selector rather than choosing a value or silently aggregating an array. Missing paths remain visible as missing provenance and do not become zero/default values.

## Field mappings and conflict handling

An entity definition lists mapping rule IDs. Every rule must be APPROVED, point to a compatible CSV column or JSON structural path in the declared source file, and target the same canonical entity type. A field cannot be populated by two rules in one entity definition. Fields generated by identity or relationship logic (entity IDs, source locators, and canonical relationship fields) cannot be overwritten by mapping rules.

Within a grouped entity, every nonblank transformed value for a mapped field must agree. If values differ, or a group mixes blank and nonblank values, the build fails. Define a finer entity grouping or resolve the source mapping; no arbitrary first-value selection, aggregation, or imputation is performed. Fully blank or missing fields remain null and retain per-value provenance.

## Candidate-value bindings

For `conditions` and `observations`, an entity definition may declare `value_candidate_bindings` separately from its primary `field_rule_ids`. Each binding names a stable `candidate_source`, a binding ID, and the exact source-inventory fields for the candidate value, optional unit, optional quoted text, and optional scalar metadata fields. All bound fields must belong to the same source file and selected record scope as the entity definition.

The builder emits one candidate record per binding and selected source record, attached to the parent Condition/Observation. Candidate IDs are deterministic; every supplied field contributes its exact source file hash and concrete row/JSON locator. Source metadata is kept opaque (for example extraction review state/reason or source evidence references) and is not interpreted or used to approve the value.

A blank candidate value is not silently dropped. The builder retains a provenance-only candidate slot with its candidate-source ID and the locator of the blank value field; optional blank unit/quote/metadata fields also retain their locators and explicit null metadata values. Such entries are counted in candidate coverage but cannot enter numeric sensitivity analysis. Multiple candidate sources never become extra canonical Observations or independent Studies.

These bindings do not change the parent record's primary `value_state`, `raw_value`, or `normalized_value`. The ordinary primary-field grouping/conflict rules remain unchanged; candidate disagreement is preserved in `value_candidates` rather than causing an arbitrary primary-value choice.

## Relationships

Links are explicitly declared from a child entity definition to a parent definition. Two matching modes are supported:

- ROW_OVERLAP: links records that share the same CSV data-row locator or exact selected JSON object pointer. It is valid only when child and parent definitions use the same source file and format.
- FIELD_EQUALITY: links records using an explicit child_key_field and parent_key_field, both populated by approved mappings in their respective entity definitions. This supports cross-file joins, including CSV-to-JSON and JSON-to-CSV relationships.

Field-equality matching is exact and type-sensitive after each field's declared transformation. No implicit normalization, trimming, case folding, DOI cleanup, unit conversion, fuzzy matching, or null-to-null matching is performed. Scalar relationships require exactly one parent match; zero or multiple matches fail. Many-valued relationships keep all exact matches. If a join is ambiguous, the records remain unlinked and the build fails rather than choosing a parent.

The same-row relationship contract is deliberately narrow: it records shared source-record membership only. It does not establish causal, temporal, or experimental equivalence beyond that evidence.

## Transformations

- IDENTITY: preserve the raw CSV cell or JSON scalar/object value.
- NUMERIC_PARSE: parse finite numeric values with explicit decimal/thousands separators.
- UNIT_CONVERSION: apply the explicitly reviewed factor and optional offset.
- LOOKUP: apply a complete explicit raw-value-to-output dictionary.
- SPLIT: split strings using an explicit delimiter and declared trimming/empty handling.
- CUSTOM: not executable by the current builder and causes a failed build.

The builder records raw value, transformed value, mapping rule, source file/hash, concrete row/column or JSON Pointer locator, and transformation parameters per mapped value. Each entity also retains its definition ID, selected source record locators, mapping version, mapping-plan hash, and source-inventory hash. The bundle-level build_provenance records exact input hashes.

## Relationship diagnostics

After a successful build, the report includes diagnostic-only checks:
- exact-payload duplicate candidates within an entity type, excluding generated IDs and provenance;
- studies without system/experiment/evidence links;
- systems with no condition/experiment use;
- conditions not referenced by experiments;
- experiments without observations;
- evidence not cited by observations.

These categories are review prompts, not automatic errors. Two records with identical payloads may still represent distinct experiments, replicates, specimens, or source statements. The diagnostic never merges or deletes records.

A standalone report can be generated with:

    dor diagnose-bundle --input canonical_bundle.json --out relationship_diagnostics.json

## Standalone Build Spec validation

Before G1, validate the mapping and Build Spec together without building a Canonical Bundle:

    dor validate-mapping --plan mapping_plan.json --inventory source_inventory.json --out mapping_validation.json
    dor validate-build-spec --plan mapping_plan.json --inventory source_inventory.json --spec canonical_build_spec.json --out build_spec_validation.json

The Build Spec validator recomputes mapping eligibility, binds to the exact plan and inventory hashes, checks that each entity source file/format exists in the source inventory, validates record selectors and grouping keys, checks mapping-rule compatibility, and checks every declared relationship. It does not read source data, execute transformations, or create entities.

G1 must bind both deterministic validation reports. When the gate is recorded, DoR recomputes them against the exact mapping plan, source inventory, and Build Spec and rejects stale or modified reports.

## Output and failure behavior

Run:

    dor build-canonical --plan mapping_plan.json --inventory source_inventory.json --spec canonical_build_spec.json --source-root path/to/source/files --out-dir path/to/new/derived/run

The builder writes build_report.json. It writes canonical_bundle.json only if the mapping plan, build spec, source hashes, record selectors, grouping, transformations, relationship cardinalities, and canonical integrity validation all pass. Existing non-empty output directories are never overwritten.

A successful engineering build only means that deterministic construction and structural/reference checks passed. It does not validate scientific meaning, independence, endpoint equivalence, source accuracy, or causal interpretation.
