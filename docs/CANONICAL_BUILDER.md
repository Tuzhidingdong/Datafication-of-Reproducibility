# Canonical Builder Contract

## Purpose

The canonical builder converts a reviewed mapping plan into canonical research entities. It executes deterministic transformations only after mapping approval and requires a separate build specification for entity identity and relationships. It does not infer scientific grain from table shape.

## Three versioned inputs

1. `source_inventory.json`: source file hashes and structural field inventory created by `dor audit`.
2. `mapping_plan.json`: approved source-item to canonical-field rules.
3. `canonical_build_spec.json`: entity grouping and relationship declarations.

The build specification stores SHA-256 digests of the exact inventory and mapping plan files. Any edit to either file invalidates the build spec and requires regeneration/review.

## Entity grain

Each entity definition names a source CSV and a grouping rule:

- `SOURCE_ROW`: one entity per data row. This is an explicit declaration, not a default.
- `GROUP_BY_FIELDS`: one entity per unique combination of the listed inventory column IDs. Every grouping key must be non-empty.

Use keys that reflect the scientific identity of that entity. For example, a Study may group by DOI, while a System may group by DOI plus a system identifier, and an Experiment may group by an explicitly reviewed experiment/protocol key. The builder does not decide those keys for the user.

## Field mappings and conflict handling

An entity definition lists mapping rule IDs. Every rule must be APPROVED, point to a CSV column in the declared source file, and target the same canonical entity type. A field cannot be populated by two rules in one entity definition. Fields generated by identity or relationship logic (entity IDs, source locators, and canonical relationship fields) cannot be overwritten by mapping rules.

Within a grouped entity, every nonblank transformed value for a mapped field must agree. If values differ, or a group mixes blank and nonblank values, the build fails. Define a finer entity grouping or resolve the source mapping; no arbitrary first-value selection, aggregation, or imputation is performed. Fully blank fields remain null and retain per-cell BLANK provenance.

## Relationships

Links are explicitly declared from a child entity definition to a parent definition. V0.2 supports only relationships based on overlap of source data-row numbers in the same CSV file. The child field must be one of the canonical relationships encoded in the runtime, such as `systems.study_ids`, `experiments.system_id`, or `observations.experiment_id`. Scalar links require exactly one parent. Many-valued links retain all matching parent IDs. Comparison links must resolve to at least two observations.

The same-row relationship contract is deliberately narrow: it records that the reviewed source representation places the child and parent facts on the same data row. It does not establish causal, temporal, or experimental equivalence beyond that evidence. Cross-file joins and JSON object/path selection require explicit contracts in a later version.

## Transformations

- `IDENTITY`: preserve the raw cell string.
- `NUMERIC_PARSE`: parse finite numeric values with explicit decimal/thousands separators.
- `UNIT_CONVERSION`: apply the explicitly reviewed factor and optional offset.
- `LOOKUP`: apply a complete explicit raw-value-to-output dictionary.
- `SPLIT`: split using an explicit delimiter and declared trimming/empty handling.
- `CUSTOM`: not executable by the current builder and causes a failed build.

The builder records raw value, transformed value, mapping rule, source file/hash, row/column locator, and transformation parameters per mapped cell. Each entity also retains its definition ID, grouped source rows, mapping version, mapping-plan hash, and source-inventory hash. The bundle-level build_provenance records the exact mapping-plan, inventory, and build-spec hashes. Normalized units should be mapped explicitly; the builder does not guess a unit field from a conversion's target unit.

## Output and failure behavior

Run:

    dor build-canonical --plan mapping_plan.json --inventory source_inventory.json --spec canonical_build_spec.json --source-root path/to/source/files --out-dir path/to/new/derived/run

The builder writes `build_report.json`. It writes `canonical_bundle.json` only if the mapping plan, build spec, source hashes, row grouping, transformations, relationship cardinalities, and canonical integrity validation all pass. Existing non-empty output directories are never overwritten.

A successful engineering build only means that deterministic construction and structural/reference checks passed. It does not validate scientific meaning, independence, endpoint equivalence, source accuracy, or causal interpretation.
