# V0.6 — End-to-end synthetic project acceptance

## Purpose

V0.6 adds a cross-module acceptance fixture for the repository's actual dor command-line workflow. It is deliberately separate from the real zinc-battery literature corpus. The fixture checks that source hashes, inventory IDs, canonical entity references, Study splits, model artifacts, interaction IDs, Evidence links, and publication-package checksums remain consistent when each stage consumes files created by the previous stage.

The test invokes the dor CLI entry point in-process for every pipeline stage. It does not merely call isolated helper functions. A separate assertion checks that the pipeline commands are registered with the CLI parser.

## Synthetic project design

The fixture creates two read-only source files:

- experiment_records.csv: eight discovery Studies, each with four two-factor condition combinations and one reported numeric outcome; plus one independent probe Study with a different target and endpoint.
- extractions.json: two explicit Condition records per experiment and structured Evidence records. The JSON records are joined to CSV records through reviewed, exact FIELD_EQUALITY keys.

The discovery endpoint follows a deliberately bilinear synthetic pattern. This makes a predictive interaction candidate recoverable without pretending that the fixture represents a physical chemical system.

Expected source-to-analysis counts:

| Entity/stage | Synthetic count |
|---|---:|
| Canonical Studies | 9 |
| Canonical Systems | 9 |
| Canonical Experiments | 33 |
| Canonical Conditions | 66 |
| Canonical Observations | 33 |
| Canonical Evidence records | 10 |
| Eligible discovery Studies | 8 |
| Eligible discovery Observations | 32 |

The ninth Study is a prospective probe with a distinct target/endpoint. It remains in the canonical bundle but must not leak into the discovery cohort.

## Executed workflow and acceptance checks

The test executes the following command path using temporary directories:

1. dor audit: inspect CSV and JSON, generate source inventory, and preserve input hashes.
2. dor validate-mapping: validate the exact inventory hash and explicit approved mapping rules.
3. dor build-canonical: join CSV and JSON records through explicit keys; then dor validate-bundle checks canonical structural and referential integrity.
4. dor reconcile-bundle: create the reconciliation report and review queue without mutating the bundle.
5. dor build-cohort: select only the exact target/endpoint and assign entire Studies to train, validation, or test.
6. dor fit-baselines and dor evaluate-reproducibility: create the selected model artifact and nested Study-held-out evaluation.
7. dor discover-interactions, dor assess-interaction-robustness, and dor generate-interaction-surface: recover the synthetic bilinear candidate, repeat the nested screen across three seeds, and generate a descriptive 9 × 9 surface.
8. dor build-mechanism-evidence-bridge: validate direct support, contradictory direct evidence, theoretical support, and a separate prospective probe; the resulting mechanism Finding must remain a candidate hypothesis pending human review.
9. dor predict-virtual-condition: use the selected serialized model with exact feature IDs and units; preserve the NOT_CALIBRATED and non-physical-reproduction boundaries.
10. dor build-publication-package and dor audit-publication-package: assemble only explicitly declared artifacts and verify their copied hashes, guide hash, completeness states, and package file index.

The suite also checks the main cross-stage failure boundaries:

- Replacing the canonical bundle after cohort construction is rejected by the mechanism bridge because the bundle SHA-256 no longer matches the cohort manifest.
- Modifying a copied publication artifact is detected by the package audit.
- Source CSV, source JSON, mapping plan, build specification, task, mechanism plan, and virtual query bytes remain unchanged during the pipeline.
- The independent probe Study is not included in the discovery cohort.
- Every canonical Observation evidence reference resolves to a canonical Evidence ID.
- Every generated mechanism Finding remains claim_type = mechanism_hypothesis, status = candidate, and mechanism_status = hypothesis.

## Run locally

From the repository root:

~~~bash
python -m pip install -e ./runtime
python -m unittest discover -s runtime/tests -p 'test_end_to_end_synthetic_project.py' -v
python -m unittest discover -s runtime/tests -v
~~~

The GitHub Actions workflow runs the synthetic integration acceptance as a dedicated step before the complete runtime test suite. This makes failures in the cross-module workflow visible separately from the general unit-test result.

## What this acceptance does not establish

This is engineering integration evidence only.

- The synthetic mapping plan is intentionally predeclared and approved inside the fixture. It does not test whether an Agent can infer scientifically correct mappings from real papers.
- The generated bilinear pattern is artificial. Recovering it does not validate a physical interaction, mechanism, or chemical interpretation.
- The prospective probe checks Study/DOI and Evidence-link plumbing. It is not a real external validation experiment.
- The virtual prediction remains a model-based scenario output, not a physical experiment or atomistic simulation.
- The test does not validate Antigravity GUI behaviour, Worker orchestration, model-provider selection, or a downstream manuscript-writing agent.
- No real literature corpus, private paper collection, or zinc-battery dataset is loaded.

V0.6 therefore verifies that the software stages interoperate under a known synthetic data contract. Scientific acceptance on the actual research corpus remains reserved for V1.0 after human review of source semantics, mapping, entity grain, endpoint definitions, and analysis design.
